## 1. 定位与核心立场

### 1.1 规范分工

| 主题 | 归属 |

| 资源关闭失败路径、清理责任模型、`Result` GC 盒实现 | S3 §17、§18、§9；本文档 §4.4、§8 补齐观测侧 |
| 取消**机制**（令牌、任务树、作用域取消） | 任务规范 |

| 跨语言错误**转换** | 本文档 §7.3 |

### 1.2 核心立场

- 错误是值。可恢复失败只走 `Result` 路径；`panic` / fatal 不可捕获、终止进程（S1 §10.4）。
- 错误观测是边界行为，不是控制流。禁止全局通知中心、隐式恢复、隐式日志。
- 高可用服务的故障隔离按进程边界设计：单个请求处理器不得捕获 fatal 后继续服务（S4 §3.4）。可恢复与不可恢复的划分见 §2.5。
- 内存回收与资源关闭是两项责任：运行时只管内存；资源关闭是使用点的显式责任（S3 §17—18）。

### 1.3 与 XDK 的边界（示意绑定声明）

本文档中出现的 `xdk.*` 包名、类型名（`Error`、`ErrorKind`）与函数签名（`wrap` / `mapErr` / `report`）以第 6 部分（XDK v1.0.0）为准，本部分只规定其**语义与不变量**：错误观测的语义（第 4 节）、`ErrorKind` 各分类的语义与契约（第 3 节、附录 A）、取消/超时错误面（第 5、6 节）、边界转换规则（第 7 节）、清理模式（第 8 节）。名称与签名变更走第 6 部分的版本流程，不影响本规范的语义。

## 2. 错误类型与 `Error` 协议

### 2.1 错误类型的合法形态

按 S1 §10.5：错误类型 `E` 可以是枚举、结构体、类或 `Error` 协议实现；`E` 不能是 `void`。本文档补充：

- `E` 不得是 `Result`（禁止嵌套 `Result<Result<..>>` 作为错误类型；`E` 含 `Result` 字段的类型按 S3 §9 的 GC 盒分析处理）。
- 错误类型应当是数据承载者：字段是诊断信息（上下文、原因、位置），不承载可变状态。
- 错误类型选择规则（定案）：优先枚举（封闭错误集）或结构体（携带上下文）；类仅用于需要继承复用诊断字段的场合。

### 2.2 `Error` 协议（正式定义）

S1 §10.5 引用了"`Error` 协议实现"但未定义协议本身；本文档补齐。`Error` 协议由 `xdk.errors` 包声明：

```x
protocol Error {
    ErrorKind kind();        // 通用分类，见第 3 节
    String describe();       // 单行诊断描述；不得包含多行或控制字符
}
```

- `describe()` 必须稳定：同一错误值在同一进程内多次调用返回相同内容（错误类型字段不可变，违反者是错误类型声明方的 bug）。
- 实现 `Error` 协议的类型同时必须满足 S1 §10.5 的 `E` 合法形态。
- 语言内建 `panic` 诊断不经过 `Error` 协议；fatal 路径由运行时直接打印（S3 §25）。

### 2.3 辅助函数（`xdk.errors`）

`Result` 是预定义类型，不能被 `extension` 扩展（S2 §11.1）；错误辅助能力以 `xdk.errors` 顶层函数提供：

| 函数 | 签名（示意） | 语义 |
| --- | --- | --- |
| `wrap` | `<E>(Result<T,E>, E) -> Result<T,E>` | 失败时丢弃原错误、返回新错误。用于把内部分类错误转换为对外契约错误 |
| `mapErr` | `<E1,E2>(Result<T,E1>, (E1) -> E2) -> Result<T,E2>` | 失败时用调用方提供的转换函数映射错误；成功原样通过 |
| `report` | `<E: Error>(Result<T,E>) -> void` | 失败时把 `kind()` 与 `describe()` 写入诊断输出；成功不做任何事。仅用于边界观测点 |

- `wrap` 丢弃原错误是显式决定；需要保留原因链时，错误类型自带 `cause` 字段并用 `mapErr` 组装。
- 不提供隐式错误字符串化；`describe()` 是唯一的文本出口。
- 语言方法集（`isOk` / `isErr` / `value` / `error` / `unwrapOr`）以 S1 §9.1 为准，本文档不扩展语言方法。

## 3. `ErrorKind` 分类体系

### 3.1 内建分类

`ErrorKind` 是 `xdk.errors` 声明的简单枚举：

```x
enum ErrorKind {
    InvalidArgument,     // 调用方传入非法参数
    NotFound,            // 目标不存在
    AlreadyExists,       // 目标已存在冲突
    PermissionDenied,    // 权限不足
    Io,                  // 文件/流读写失败
    Network,             // 网络连接、协议失败
    Timeout,             // 超时（契约见 §6）
    Cancelled,           // 被取消（契约见 §5）
    Busy,                // 资源忙/限流，可重试
    Unavailable,         // 依赖不可用，可能可重试
    DataCorrupted,       // 数据损坏/校验失败
    Unsupported,         // 不支持的操作
    OutOfMemory,         // 分配失败（观测面；进程可能即将终止）
    Internal,            // 不可预期的内部错误（等价"不该发生"）
}
```

### 3.2 匹配与使用规则

- `ErrorKind` 用于**粗粒度决策**（重试、降级、上报分级、退出码映射）；精细处理必须用错误类型本身（枚举项或字段），不得用 `kind` 做细粒度分支。
- `Timeout` 与 `Cancelled` 是受契约保护的分类：见 §5、§6，任何实现不得把取消伪装成其他分类。
- 用户错误类型的 `kind()` 返回值在错误值生命周期内不变。
- `OutOfMemory` 特殊：分配失败路径的观测不保证能完成复杂工作；观测实现必须不分配内存（由运行时诊断通道保证，见 §9）。

### 3.3 分类稳定性

`ErrorKind` 的枚举项集合是跨版本兼容性承诺：只能追加、不得改名或删除；语义解释以本文档附录 A 为准。

## 4. 错误观测

### 4.1 观测是显式动作

观测只允许以下显式形态：

1. `isErr()` / `error()` 直接读取（S1 §10.1）；
2. 边界点的 `xdk.errors.report(r)`（写入诊断输出）；
3. 显式构造的观测中间层（包装函数先 `report` 再传播），由调用方在调用点可见。

### 4.2 禁止的观测形态

- 禁止全局错误通知中心、全局错误处理器、隐式日志钩子（S1 §10.5 的禁止项，本文档确认为永久设计）。
- 禁止在 `mapErr` / `wrap` 的转换函数中产生日志副作用（转换必须纯净；观测只发生在 §4.1 的形态中）。
- 禁止用观测替代处理：`report` 之后错误仍必须传播或显式处置；"report 了就算处理了"不是合法模式。

### 4.3 日志与诊断约定

- 诊断输出是唯一内建观测通道：单行、含 `kind` 与 `describe()`、无隐式调用栈（调用栈只属于 fatal 路径，S1 §10.4）。
- 更丰富的日志能力（级别、上下文、结构化字段）由 XDK 日志包提供，调用点显式；日志包不得读取"全局当前错误"之类隐式状态。
- 诊断输出不得包含敏感信息（凭据、个人数据）；错误类型设计者对 `describe()` 的内容负责。

### 4.4 资源关闭失败路径

对齐 S3 §18（关闭失败通过 `Result` 报告，调用方决定是否观测）。本文档规定关闭合同与处理模式：

- **关闭合同**：`close()` 类清理操作的失败**不等于未关闭**——清理动作不可撤销，`Result` 仅报告诊断（如 flush 失败但句柄已释放）。XDK 资源 API 必须按此合同声明；违反此合同（失败后资源仍可用）的 API 是合同 bug。
- **defer 内处理模式**（`defer` 体内禁止 `try` / `return`，S1 §10.3；且清理调用的 `Result` 未处理会产生诊断）：

```x
static void process(final String path) {
    final File input = File.open(path).unwrapOr(...); // 打开失败必须显式处置，见下
    defer {
        final Result<void, IoError> r = input.close();
        if (r.isErr()) {
            xdk.errors.report(r);      // 显式观测；失败不影响已释放事实
        }
    }
    // ... 使用 input
}
```

- 打开失败的处置模式：`unwrapOr` 提供回退值不适用于"必须中止"的场景；正确形态是显式检查后走 `Result` 返回：

```x
static Result<void, IoError> process(final String path) {
    final Result<File, IoError> opened = File.open(path);
    if (opened.isErr()) {
        return Err(opened.error()!);
    }
    final File input = opened.value()!;
    defer { /* 关闭模式如上 */ }
    // ...
    return Ok(void);
}
```

- 无 `_` 丢弃语法是设计决定：每一个被忽略的 `Result` 都必须写成可见的显式形态，使"忽略"在代码审查中可见。

## 5. 取消

### 5.1 分工与模型

- 取消的**机制**（取消令牌、任务树、作用域取消、自动传播）由任务规范定义；S3 §11.4 已确认两者共担。
- 本文档定义取消的**错误面**，对所有可取消操作统一适用，无论机制实现细节如何。

### 5.2 `Cancelled` 契约

- 被取消的操作以 `Err` 报告，错误 `kind()` 为 `ErrorKind.Cancelled`；取消是错误值，不是控制流异常、不是 `null`、不是布尔标志。
- **不得吞掉取消**：捕获 `Cancelled` 后返回 `Ok` 或转换为其他分类，只有在"取消前工作已完成"的竞争情形下允许（完成优先语义，由任务规范裁决竞争窗口）。
- **不得伪装取消**：非取消原因的失败不得报告为 `Cancelled`。
- 取消操作必须已停止产生对外可见副作用后方可返回 `Cancelled`；"边取消边继续写"是实现 bug。
- 清理路径（`defer` / `errdefer` 体）不得因再次取消而跳过；清理中的取消请求排队到清理完成后由任务规范处理。

### 5.3 与 `Result` 的交互

- 可取消函数的签名不变：仍是 `Result<T,E>`；`E` 的错误类型必须能表达 `Cancelled`（直接或经 `kind()`）。
- `unwrapOr` 等兜底方法对 `Cancelled` 不做特殊处理：兜底即显式决定吞掉取消，调用点可见。框架级"取消必须继续向上传播"的保证由任务规范在任务边界执行。

## 6. 超时

### 6.1 超时错误面

- 超时以 `Err` 报告，`kind()` 为 `ErrorKind.Timeout`；超时**不是 panic**、不是 fatal。
- 超时的**机制**（定时器、监控点）由任务规范与 XDK 规范定义；本文档只约束契约：
  - 超时与取消同构：超时是调用方驱动的取消；§5.2 的全部契约（副作用停止、不伪装、清理不跳过）对超时同样适用；
  - 已超时操作返回后，底层资源状态必须处于文档声明的确定状态（已提交 / 未提交，不得是"不确定"）。

### 6.2 精度承诺边界

- XNull 不承诺硬实时（S3 §0）；超时是"不早于到期点后尽快生效"，到期前的少量过冲是合法行为。
- 对超时精度有合同要求的场景（硬件协议等）不属于语言承诺范围，须由专用运行时外实现承担。

## 7. 边界转换

### 7.1 边界清单

| 边界 | 转换责任 | 规范 |
| --- | --- | --- |
| 进程入口（`main` 返回） | 本文 §7.2 | S1 §12 入口规则 |
| FFI 跨语言调用 | 本文 §7.3 | 第 7 部分 §7；S3 §19 |
| 任务边界（join / 回调交付） | 任务规范 | S3 §11.4 |
| 进程外通信（网络、IPC） | 应用层；本文只给原则 | §7.4 |

### 7.2 进程入口：退出码映射

`main` 的两种签名（S1 §11.2）：`static void main` 与 `static Int main`。本文档规定 `Int main` 的退出码映射约定：

| 退出情形 | 退出码 |
| --- | --- |
| 正常返回 | `0` |
| 返回非零值 | 该值原样作为退出码 |
| 初始化或运行期 fatal（panic） | 固定退出码 `134`（定案；不得为 `0`） |

- `main` 不能返回 `Result`（`try` 不能用于 `main`，S1 §10.2）；入口需要报告失败时，用 `Int main` 显式把错误映射为退出码，映射规则由应用决定、必须显式写在入口处。
- 退出码区间约定（定案，不参与验收）：`1—63` 应用自定义；`64` 用法错误（`InvalidArgument`）；`69` 依赖不可用（`Unavailable`）；`70` 内部错误（`Internal`）；`134` 保留给 fatal。不遵循不构成语言错误，但工具链可按风格警告。遵循 BSD `sysexits` 习惯，便于运维脚本。

### 7.3 FFI 边界

- `Result` 是 XNull 内建值类型，**不跨语言边界**：进入 FFI 的函数签名不得含 `Result` 类型参数或返回值（错误以错误码/出参表达；详见第 7 部分 §7.1，本条为前置约束）。
- 跨语言错误转换必须显式：XNull 侧包装函数把 FFI 错误码映射为本地错误类型（`kind` 按附录 A 语义选择）；禁止把未知错误码静默映射为 `Ok`。
- 原生侧向 XNull 报告的取消/超时，必须映射为 `Cancelled` / `Timeout` 分类，不得降级为 `Internal`。

### 7.4 进程外通信原则

- 对外协议（HTTP、RPC）的错误映射由应用显式编写；XNull 不提供"错误自动转状态码"的隐式机制。
- 面向外部系统的错误信息只能来自 `describe()` 或显式构造的响应体；内部错误类型字段不自动外泄。

## 8. 结构化清理与错误路径

S3 §17 已定义清理责任模型（defer LIFO、`goto` / `throw` / 进程退出不执行 defer、fatal 无清理保证）。本文档补充错误路径的使用规则：

- `errdefer` 用于**补偿**（失败时的逆向动作：回滚、释放、计数器递减）；`defer` 用于**无条件清理**。两者选择标准：动作在成功路径上是否也必须发生。
- 补偿动作自身失败：补偿是尽力而为，补偿内的 `Result` 处理遵循 §4.4 模式；补偿失败不得阻断原错误传播（`errdefer` 体内不得 `return`，S1 §10.3）。
- 错误路径不引入新的清理责任层级：任何资源的使用点关闭模式（S3 §17）在 `try` 传播、`Err` 返回、正常返回三条路径上行为一致（验收 MEM-10），本文档不新增机制。
- 部分完成状态：函数多步修改外部状态后中途失败，要么在 `errdefer` 中回滚到进入前状态，要么在错误类型中携带"已完成步骤"信息交由调用方决策；静默留下半完成状态是设计错误。

## 9. 实现边界与发布门槛

与 S2 §16 同规则：本节是发布门槛，不是"未强制"清单。

- `xdk.errors` 包（`Error` 协议、`ErrorKind`、`wrap` / `mapErr` / `report`）未实现前，依赖它的 XDK API 不得发布。
- 诊断输出通道必须无堆分配（保障 `OutOfMemory` 场景可观测）；做不到时允许降级为最小单行输出，但不得静默丢失 fatal 报告（对齐 S3 §25）。
- `Cancelled` / `Timeout` 契约的运行时验证点（副作用停止、清理不跳过）纳入任务规范的验收；本文档验收覆盖错误面映射。
- 未处理的 `Result` 诊断（S1 §10.5）必须可配置为编译错误（`@mustUse` 强度），默认强度由实现决定并在工程配置规范固化。

## 10. 验收矩阵

| 编号 | 领域 | 验收内容 | 判定 |
| --- | --- | --- | --- |
| OBS-01 | 观测 | `report` 输出单行含 kind 与 describe；成功时零输出；转换函数无副作用可验证 | 行为不符合 §4 即失败 |
| OBS-02 | 观测 | 全局通知中心、隐式恢复、观测副作用形态被拒绝 | 编译错误或无此 API |
| OBS-03 | 观测 | defer 内未处理的清理 `Result` 产生诊断；§4.4 模式零诊断 | 诊断缺失即失败 |
| KIND-01 | 分类 | `ErrorKind` 枚举项与附录 A 一致；`kind()` 在错误生命周期内不变 | 编译错误或运行时不变量失败 |
| CANCEL-01 | 取消 | 取消以 `Err` + `Cancelled` 报告；副作用已停止；吞掉/伪装形态被契约测试拒绝 | 运行时契约测试 |
| CANCEL-02 | 取消 | 清理路径不因再次取消跳过 | 运行时契约测试 |
| TIMEOUT-01 | 超时 | 超时为 `Err` + `Timeout`，非 panic；资源终态确定 | 行为不符合 §6 即失败 |
| BOUND-01 | 边界 | `Int main` 退出码映射正确；fatal 退出码非零 | 进程级测试 |
| BOUND-02 | 边界 | 含 `Result` 的签名不得通过 FFI 暴露；未知错误码不得映射为 `Ok` | 编译错误或合同测试 |
| BOUND-03 | 边界 | 取消/超时经 FFI 映射不降级为 `Internal` | 合同测试 |
| CLEAN-01 | 清理 | `errdefer` 补偿失败不阻断原错误传播；部分完成状态有回滚或状态报告 | 行为不符合 §8 即失败 |

| 情形 | 路径 | 依据 |
