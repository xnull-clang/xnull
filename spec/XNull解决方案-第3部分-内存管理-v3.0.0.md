## 决策摘要

- XNull 采用三种内存策略：stack（内联/栈值）、ARC（引用计数）、GC（标记—清扫）；策略由编译器按确定性规则判定，不是源码类型。
- `struct`、简单枚举是纯值，内联存储，不进入 ARC/GC；`class` 与 `singleton` 是策略判定对象；数据枚举项固定为 GC 全局根。
- 混合引用图的不变量由第 2 部分 15.6 规定；本文档规定其运行时实现合同与验收方式。
- `Result` 的语言语义是值类型；当前实现以 GC 盒表示，内联 ABI 是明确优化方向，内联前不得声明性能承诺。
- 标量数组按元素实际宽度存储；原始字节区免扫描。含引用的容器按 GC 追踪。
- 语言不承诺硬实时：GC 会合、ARC 原子操作与回收延迟没有最坏耗时合同；实时控制层不属于本语言承诺范围。
- 资源关闭与内存回收是两项责任；文件、句柄、锁、任务组必须在使用点显式关闭，`deinit` 只是兜底。
- FFI 是合同约束的边界：句柄与调用租约由本文档第 19 节规定，不提供任意原生函数的直接调用承诺。

## 0. 规范基础

### 0.1 范围

本文档规定 XNull 的内存管理：内存模型、策略判定与传播、逃逸分析、ARC/GC 实现合同、终结顺序、弱引用、任务与跨线程共享、清理责任、FFI 所有权、优化方向、验收与应用边界。

本文档不规定：

- 对象种类、继承、协议与派发；见第 2 部分。
- `defer` / `errdefer` 的语法与传播语义；见第 1 部分第 10 节。
- XDK 的包结构、类型名与 API 形态；文中出现的 `xdk.*` 名称以第 6 部分（XDK v1.0.0）为准，本部分不重复定义其 API 形态。
- 错误观测、取消与超时；见错误处理规范。
- XDK 包 API；见 XDK 规范。
- 具体分配器算法、GC 分代/增量策略；实现可以自行选择，但必须满足本文档的不变量。

### 0.2 与第 1、2 部分的关系

第 2 部分 15 节规定内存策略的源码可观察语义（策略判定表、逃逸分类、布局、混合引用图不变量、`deinit` 顺序、弱引用规则）。本文档在其上规定：

- 运行时必须提供的数据结构与管理动作；
- 策略在调用边界、容器、闭包与任务间的传播规则；
- 清理责任与资源句柄模型；
- 优化方向及其不得改变的语义边界；
- 验收项与明确不承诺的边界。

两篇冲突时，以第 2 部分对源码可观察语义的规定为准；本文档补充实现合同。

### 0.3 规范用语

**必须**、**禁止**、**应当**、**可以** 按 RFC 2119 语义使用。第 2 部分 16 节的发布门槛（BND-01..15）同样约束本文档；本文档第 25 节的验收项是内存维度的补充门槛。

### 0.4 确定性

同一源程序、同一实现版本、同一编译选项必须产生相同的策略判定、布局决策、vtable 槽位和运行结果。回收时机不要求确定，但回收造成的可观察结果（`deinit` 顺序、弱引用置空）必须满足本文档的顺序规则。

## 1. 内存模型总览

| 数据 | 存储 | 管理 |
| --- | --- | --- |
| 值类型标量、简单枚举 | 内联（变量槽、字段槽、数组元素） | 无管理；随存储槽消亡 |
| `struct` 值 | 内联，按值复制 | 无管理；复制不触发回收 |
| 栈分配的类对象（逃逸分析通过） | 栈帧 | 随帧消亡；无 `deinit` 调用义务以外的动作 |
| ARC 类对象 | 堆 | 引用计数；归零时终结 |
| GC 类对象、数据枚举项、单例 | 堆 | 标记—清扫；不可达时清扫 |
| 闭包对象与 env、cell | 堆 | GC |
| `Any` 装箱 | 堆 | GC |
| `Result`（当前实现） | GC 盒 | GC；内联 ABI 见 §20 |

不变量：

1. 源码没有地址、指针与手动释放；所有回收由编译器插入的管理动作和运行时完成。
2. 每个强引用要么增加 ARC 计数，要么被 GC 追踪（第 2 部分 15.6 不变量 1）。
3. 弱引用不增加计数、不阻止回收，目标死亡时置 `null`。
4. 栈分配是优化，不改变引用语义与对象身份。

## 2. 分配头与布局

堆对象统一分配头（第 2 部分 15.3）：

- 对象种类（ARC / GC）；
- 类型描述符；
- ARC 计数或 GC 标记字；
- 扫描信息（含引用字段的偏移表或位图）。

合同：

- 类型描述符必须支持 `is` / `as` 的动态类型检查、协议实现检查和 `Any` 拆箱检查。
- ARC 对象持有 GC 引用时，必须登记为 GC 扫描对象；GC 对象持有 ARC 引用时，必须在清扫时 release（第 2 部分 15.6 不变量 2、3）。
- 实现协议的类，载荷起始位置是协议 vtable 指针；未实现协议的类没有该指针。
- 栈对象没有分配头；编译器必须在需要动态类型检查时保留类型信息，静态可证明时省略。
- 字段按 8 字节对齐；标量值字段占一个 8 字节槽位。更紧凑的打包布局是优化方向（§20），当前不承诺。

## 3. 值类型、装箱与纯值数据

- `struct` 值内联存储，赋值、传参、返回、存入容器都复制；复制不触发 ARC/GC 动作，不调用 `deinit`。
- 简单枚举按 `Int` 内联；数据枚举项是 GC 对象，程序启动时构造，全局根常驻。
- 值类型进入 `Any` 必须装箱；装箱对象由 GC 管理，拆箱检查装箱类型。
- 结构体字段只能 satisfying 第 2 部分 3.2 的值字段；运行时不需要为结构体提供任何扫描、计数或终结动作。
- 元组是内建值类型，内联存储；全值元素元组零管理；含引用元素的元组按槽位扫描，拥有它的类按第 2 部分 15.1 第 7 条归入 GC。
- 含 `Result` 字段的类，在当前实现中按 GC 分析（`Result` 为 GC 盒）；`Result` 内联落地后按第 2 部分 15.1 的规则重新判定。

## 4. 策略判定

判定规则以第 2 部分 15.1 的策略表为准。本文档补充实现合同：

- 判定发生在单态化之后、代码生成之前；判定结果必须可转储（诊断选项），供验收复现。
- 判定输入全部来自单态化后的源码结构：种类、字段类型图、引用环分析、`deinit` 存在性、`self` 捕获、逃逸分类；源码不得表达引用强度或回收策略。
- `@arc` / `@gc` 是实现内部注解（第 2 部分 15.1.2）：源码不得出现，仅限实现预览使用，属非承诺入口。
- 判定必须保守：无法证明无环或字段具体时，归入 GC；禁止把无法分析的对象交给 ARC。
- `@arc` 条件不满足是编译错误，不得静默退回 GC（第 2 部分 BND-10）。

## 5. 策略图与策略传播

策略图的节点是类型（单态化实例）和存储位置（局部、字段、静态/顶层、容器元素、闭包环境）；边是强引用。

传播规则：

| 边 | 传播 |
| --- | --- |
| ARC 对象 → ARC 对象字段 | 计数管理；目标字段入 ARC |
| ARC 对象 → GC 对象字段 | ARC 对象登记为扫描对象；字段入 GC 追踪 |
| GC 对象 → ARC 引用字段 | GC 保持目标可达；清扫时 release |
| 任何位置 → 含 `Any` / `Object` / 协议 / 未单态化泛型的字段 | 拥有者按 GC 分析 |
| 容器元素为引用 | 容器对象是 GC；元素被追踪 |
| 闭包 env 捕获 ARC 引用 | env 是 GC 块；释放 env 时 release 该引用 |
| 静态/顶层字段、单例字段 | 全局根；ARC 被 retain，GC 被追踪 |

规则：

- 策略按节点独立判定后按上表传播；传播不得改变节点自身的判定结果。
- 引用环中出现至少一个 GC 节点时，环由 GC 回收；全 ARC 强引用环必须由内存分析检测：自动策略改判 GC，`@arc` 策略报编译错误。
- 协议类型字段、`Any` 字段使拥有者进入 GC（第 2 部分 15.1 第 7 条）。
- 策略图必须无未判定节点；代码生成前存在未判定节点是编译器内部错误。

## 6. 逃逸分析与栈分配

逃逸分类与条件以第 2 部分 15.2 为准。实现合同：

- `none` 类对象可以栈分配；栈分配必须保证对象身份与引用语义不变。
- `return` 类对象提升为 ARC；字段已要求 GC 时保持 GC。
- `other` 类对象提升为 GC。
- 分析不完整或存在不可见边界（FFI、XDK 调用、任务提交）时，必须按逃逸处理。
- 栈对象被闭包捕获 `self`、进入容器或被发布时，必须改为堆分配；禁止复制已发布对象。
- 逃逸分析结果不改变语言语义；不提供源码可观察的分配行为合同。

## 7. 引用计数与弱引用基础

- ARC 计数在并发下必须原子；实现可以在证明无并发的编译单元中使用非原子计数，但不得跨编译单元混用两种计数格式。
- retain / release 必须成对；release 到零触发终结链（§14）。
- 弱引用不是语言特性：XNull 源码与 XDK 公共 API 不提供弱引用概念。弱表是运行时内部机制，入口只对 FFI 合同层和运行时内部开放（§19、§22）。
- 弱引用由运行时弱引用表管理：目标终结前从表中清除并置 `null`；弱引用读写必须原子，禁止读到已终结目标。
- 弱引用表可以按目标对象内联侧表或全局侧表实现；实现不得因弱表持有强引用。
- 运行时内部弱槽位的赋值、置空、清除是弱表操作，不修改计数。

## 8. 标记—清扫基础

- GC 采用标记—清扫；实现可以使用分代、增量或并发策略，但必须保持根集合与写屏障正确。
- 根集合：栈槽位、顶层/静态字段、单例、数据枚举项、闭包 env（可达者）、任务 external root、ARC 扫描列表。
- 回收可以在分配点或安全点触发；运行时必须保证 mutator 只在安全点与 GC 会合。
- 清扫必须满足第 2 部分 15.6 不变量 3、6：死亡 GC 对象 release 其 ARC 引用；存活对象引用保持有效。
- GC 不保证进程退出时执行 `deinit`（第 2 部分 15.5）。

## 9. Result 的表示

- `Result<T,E>` 的语言语义是值类型（第 1 部分 2.1、10.1）。
- 当前实现以 GC 盒表示：每次 `Ok` / `Err` 构造分配一个盒对象；盒内保存判别、`T` 值与 `E` 值。
- 由此产生的当前边界（与第 1 部分 §12 一致）：
  - `Result` 参与算术、复制语义检查时按值语义处理；运行时身份不暴露给源码。
  - 含 `Result` 字段的类按 GC 分析；`@arc` 不能用于含 `Result` 字段的类。
  - `Result` 盒不进入 `Result` 的 `==` / `===`（语言不提供）；不暴露盒身份。
- `Result` 内联 ABI 是明确优化方向（§20）；内联落地前，本文档不声明 `Result` 相关的性能特性。

## 10. 容器与数组的内存

- `T[]` 是 GC 对象：分配头 + 长度 + 元素区。
  - 标量或纯值元素（值类型、简单枚举、`struct`、全值元组）按元素实际宽度存储，紧凑排列；元素区是原始字节区，免扫描。
  - 引用元素按指针槽位存储，元素区登记为扫描区。
  - `struct` 元素区内联整个值；嵌套 `struct` 递归内联。
- `List<T>`：GC 对象，含长度、容量与元素缓冲区；扩容复制元素区。元素扫描规则与 `T[]` 相同。
- `Map<K,V>` / `Set<T>`：GC 对象，含哈希桶数组与条目存储；桶数组与条目含引用时登记扫描。键值对存储布局是实现细节。
- `String` / `Text`：GC 对象，头 + UTF-8 字节区；字节区免扫描。
- `Bytes`：GC 对象，头 + 可变字节区；字节区免扫描。
- `StringBuilder`：GC 对象，含可变缓冲区；缓冲区免扫描。
- 容器缩容（`remove` / `clear`）时，被移除的引用元素必须立即或在本操作内 release（GC 元素等待清扫亦可，但 ARC 元素必须 release）。
- 容器对象本身永远是 GC；不因元素全为纯值而改变容器对象的策略。纯值元素区免扫描是性能特性，不是策略改变。

## 11. 任务与跨线程共享

- 闭包进入 `xdk.tasks` 时，其 env 登记为 external root；任务存活期间运行时保证 env 及其捕获图可达。
- 任务 dispose 时移除 external root；之后 env 按普通 GC 规则回收。
- 跨任务传递的 ARC 对象按原子计数管理；GC 对象由根集合与安全点保护。
- 字段与捕获变量的并发访问不同步；数据竞争是程序错误：运行时不做检测、结果不作任何保证（非承诺；原因：不做竞争检测；依赖后果：存在数据竞争的程序不受任何行为保证）。同步责任在使用点显式（第 2 部分 15.9）。
- `@Sendable` 在 v3.0.0 保留但不强制；运行时不做数据竞争检查。
- 单例被任务捕获时是同一个全局实例；不复制。
- 跨线程引用的建立与断开必须经过运行时提供的发布点；实现不得允许 mutator 在无同步的情况下直接交换堆引用。

### 11.4 并发能力的明确边界

任务闭包跨线程保活不推出以下能力；在配套规范落地前，实现与文档不得声称具备：

- 结构化并发（任务树、作用域取消、异常聚合）；
- 自动取消传播；
- 数据竞争检测；
- 优先级、公平性或延迟合同。

这些能力属于任务规范与错误处理规范的范围。

## 12. 写屏障与安全点

- 实现 GC 的写屏障必须覆盖：GC 对象字段的引用写入、ARC 扫描列表的维护。
- 实现 `@arc` 的编译单元不需要写屏障；混合写入点必须插入。
- 安全点必须覆盖：分配点、调用边界、循环回边（实现可选择）；运行时不得假设 mutator 会主动到达安全点以外的位置。
- 栈扫描必须在安全点进行；保守扫描只允许作为实现兜底，且不得造成提前释放或悬挂（第 2 部分 15.6 正确性条件）。

## 13. 回收会合与延迟边界

- GC 会合（STW 或安全点等待）、标记、清扫、ARC 原子操作和用户 `deinit` 的耗时都没有最坏时间合同。
- 因此 XNull 不承诺硬实时；电机伺服、安全控制等严格时限层不属于本语言承诺范围（能力边界文档 §4.3、§6）。
- 实现可以提供回收调优选项（触发阈值、增量步长）；这些选项不构成延迟合同。
- 需要“回收不中断”的代码段，只能通过任务模型和外部设计规避，语言不提供禁用回收的源码语法。

## 14. ARC 终结

ARC 计数归零时按第 2 部分 6.5 / 15.7 的顺序执行：

1. 清除弱引用（弱表删除，弱槽位置 `null`）。
2. 执行派生类 `deinit`。
3. 执行父类 `deinit` 链（显式 `super.deinit()` 接管剩余链时，编译器不再自动调用）。
4. 释放剩余引用字段：ARC 字段 release，GC 字段解除扫描登记。
5. 回收内存。

合同：

- `deinit` 内字段仍然有效；运行时在链完成后才释放引用字段。
- `deinit` 中的弱字段可能已经是 `null`；运行时不得重复释放已置 `null` 的字段。
- 终结链不得重入分配头状态；`deinit` 内禁止复活 `self`（存入全局、容器、闭包或返回）。
- 终结链 panic 直接终止进程，不保证其余清理。

## 15. GC 终结

- GC 对象不可达时清扫；`deinit` 在清扫阶段调用，时机不确定。
- 清扫顺序：标记完成后，对死亡对象先 release 其 ARC 引用，再调用 `deinit`（如声明），最后回收内存。
- 同一清扫周期内多个死亡对象的 `deinit` 调用顺序是实现细节；`deinit` 不得依赖其他对象的 `deinit` 顺序（第 2 部分 6.6）。
- 死亡对象间相互引用不构成复活；清扫期间不得把死亡对象重新标记为可达。
- `deinit` 把 `self` 存入外部状态是程序错误；运行时检测到复活行为时必须终止进程。

## 16. 弱引用表

弱表是运行时内部机制：语言与 XDK 公共 API 不暴露弱引用（第 2 部分 15.8）；本节入口仅服务于 FFI 合同层（§19）与运行时内部（§22）。

- 弱表管理所有弱槽位与目标对象的映射。
- 目标进入终结链前，运行时清除其全部弱槽位。
- 弱表操作（建立、读取、清除）必须原子；并发清除与读取不得观察到已终结目标。
- 弱表不得阻止目标回收；清除后的槽位必须可复用。
- 弱引用只能指向有身份的引用类型（第 2 部分 15.8）；值类型 `weak` 是编译错误。

## 17. 清理责任模型

- 内存回收与资源关闭是两项责任；ARC/GC 只负责内存，不负责文件、连接、锁、事务、socket、任务组等外部资源。
- 外部资源必须在使用点显式关闭：`defer input.close();` 模式（第 1 部分 10.3）。
- `deinit` 只是最后兜底：GC 时机不确定、进程退出与 panic 不保证调用 `deinit`（第 2 部分 6.4）。
- `goto`、`throw` 与进程退出不执行 `defer`；依赖结构化清理的代码不得使用非结构化跳转（第 1 部分 6.10、10.4）。
- 清理调用返回 `Result` 时必须显式处理；`@mustUse` 在 `defer` 体内同样生效。
- 语言不提供析构保证链之外的隐式清理机制；清理顺序由源码的 `defer` 注册顺序决定（LIFO）。

## 18. 资源句柄与使用点关闭

- XDK 提供的资源类型（文件、socket、任务组等）必须把关闭入口设计为显式方法，并保证重复关闭安全。
- 句柄类型不得依赖 `deinit` 作为唯一关闭路径。
- 关闭失败通过 `Result` 报告；调用方决定是否观测。
- 句柄不得跨任务无同步共享；需要共享时由调用方同步或移交所有权（移交方式由任务规范定义）。
- 本节是 XDK 资源 API 的约束来源；具体类型与签名见 XDK 规范。

## 19. FFI 与跨语言所有权

- FFI 是合同约束的边界，不是任意原生函数的直接调用（能力边界文档 §6）。
- 跨边界传递的数据必须满足以下之一：
  - 值传递：标量、`struct`（布局经验证兼容）或封送副本；
  - 句柄传递：不透明句柄 + 显式生命周期合同；
  - 缓冲区传递：`Bytes` / 标量数组的原始字节区，边界期间运行时保证存活。
- 源码没有 `extern` 或 `unsafe` 块；FFI 入口由 XDK / FFI 规范定义，调用租约（谁持有、何时释放）必须显式声明。
- XNull 对象引用不得作为跨语言地址使用；ARC/GC 不管理另一语言中的对象。
- 回调进入 XNull 需要显式 trampoline 与生命周期合同（第 2 部分 14.5）；trampoline 必须在调用期间登记 env 为根。
- 布局兼容必须逐类型验证；XNull 字段槽与目标 ABI 不默认相同（能力边界文档 §6）。
- 完整 FFI 规范见第 7 部分；本节是其内存维度的前置约束，第 7 部分已在本节基础上完整化（调用形态、布局验证、ABI 命名、错误码）。

## 20. 优化方向

以下优化属于实施基线的演进方向；每项必须按 §25 的验收方式单独落地，不得直接推导为整体性能承诺：

| 优化 | 内容 | 不得改变的语义 |
| --- | --- | --- |
| 纯值免管理 | `struct`、简单枚举零管理成本 | 值复制语义 |
| 无引用载荷免扫描 | 全纯值字段的对象与原始字节区不进入扫描 | 引用语义、身份 |
| `Result` 内联 | 判别 + 载荷内联到存储槽，消除盒分配 | 值语义、`@mustUse`、panic 路径 |
| 分配消除 | 非逃逸类对象、非逃逸闭包与 cell 栈分配 | 对象身份、捕获共享语义 |
| 紧凑布局 | 字段打包、宽度压缩 | 8 字节槽语义可观察行为（当前无源码可观察差异，但 ABI 变更需验收） |
| ARC 非原子化 | 证明无并发的编译单元使用非原子计数 | 弱引用原子性、跨单元一致性 |

约束：

- 优化不得改变可观察行为：身份、求值顺序、panic 路径、`deinit` 顺序约束。
- 共享 cell、可观察捕获语义不能被优化改变（能力边界文档 §7）。
- 每项优化落地时必须更新第 1、2 部分对应的实现边界条款。

## 21. 诊断与观测

编译期必须报告（与第 2 部分 15.10 一致）：`@arc` 字段不确定或成环、单态化残留类型参数、结构体值递归、结构体引用字段、`weak` 用于非身份类型、私有字段违规、构造完成前 `self` 逃逸、`final` 字段赋值违规等。

运行时必须报告：分配失败、栈溢出、空引用解引用、下标越界、`as` 失败、除零、移位越界、显式 `throw`。报告方式为打印诊断与调用栈后终止进程，不展开栈。

`xdk.runtime` 可以提供分配统计、GC 指标、存活对象转储与泄漏诊断；这些是工具能力，不是语言语义。

## 22. 运行时 ABI 最小合同

运行时必须提供以下入口（命名是实现细节，跨 FFI 的稳定命名见 FFI 规范）：

- 分配：`alloc(desc, size)` —— 分配堆对象并安装分配头；
- 计数：`retain(obj)`、`release(obj)` —— 原子计数与终结触发；
- 弱表：`weak_bind(slot, obj)`、`weak_read(slot)`、`weak_clear(slot)`；
- GC：`write_barrier(obj, field, value)`、`register_root` / `unregister_root`、`safepoint()`；
- 扫描登记：扫描信息查询（按类型描述符）；
- 任务根：`task_root_bind(env)` / `task_root_unbind(env)`。

编译器生成的代码只通过这些入口管理内存；不得绕过分配头直接操作计数或标记。

## 23. 编译选项与配置

- 内存相关编译选项：策略判定转储、逃逸分析转储、GC 策略选择（`auto` 缺省 / `arc` / `gc`，三值定案）、分配统计开关。
- 选项不得改变语言语义；同一程序在不同合法选项下的可观察行为（除诊断输出与性能）必须一致。
- 选项不属于语言规范；工程清单如何固化选项由工程配置规范规定。

## 24. 度量与基准

性能结论必须落到命名负载与指标：

- 每秒报文数、每批采样处理耗时、连接与任务规模；
- p50 / p99 延迟、峰值内存、回收暂停时长分布；
- 分配速率与 GC 频率。

本文档与能力边界文档 §7 一致：现阶段没有依据给出“整体快于 Go、Java、Rust 或 C++”的排名；高性能定位由 §25 验收逐项证实。

## 25. 验收

| 编号 | 验证点 | 通过条件 |
| --- | --- | --- |
| MEM-01 | 策略判定 | 第 2 部分 15.1 表的每种输入得到正确策略；判定结果可转储并复现 |
| MEM-02 | 策略与内部注解 | 判定表输入全部来自源码结构；源码使用 `@arc` / `@gc` 被拒绝；内部注解仅限实现预览；混合图行为符合 ARC 合同，不得静默退回 |
| MEM-03 | 混合图 | 15.6 六条不变量在压力用例下成立；ARC↔GC 混合无悬挂、无泄漏、无重复释放 |
| MEM-04 | 弱引用 | 目标终结前清除；读不到已终结目标；并发清除安全 |
| MEM-05 | 栈分配 | `none` 类对象栈分配后身份与引用语义不变；逃逸路径全部提升 |
| MEM-06 | 容器 | 标量/纯值元素区免扫描；引用元素正确追踪；`clear` 后引用按 §10 处理 |
| MEM-07 | Result | 当前 GC 盒实现下不暴露盒身份；含 `Result` 字段的类按 GC 分析 |
| MEM-08 | 终结 | ARC 归零链与 GC 清扫顺序符合 §14/§15；复活行为终止进程 |
| MEM-09 | 任务 | env external root 绑定与解除正确；dispose 后可回收 |
| MEM-10 | 清理 | `defer` 资源关闭模式在成功、`try` 传播、错误返回路径上均执行；fatal 路径行为符合 §17 |
| MEM-11 | FFI | 句柄传递、缓冲区传递按 §19 合同执行；无租约声明的入口被拒绝 |
| MEM-12 | 确定性 | 同一源程序、同一版本、同一选项产生相同策略判定与运行结果（DET-01 的内存维度） |
| MEM-13 | 优化 | §20 每项优化落地时语义回归通过；未落地项不得声明 |

验收必须包含正例、负例与压力用例；负例必须断言具体诊断。

## 26. 应用边界

与能力边界文档 §6 一致，内存维度上本方案不承诺：

| 目标 | 判断 | 原因 |
| --- | --- | --- |
| 内核、驱动、裸机 | 不承诺 | 无源码地址/解引用语义，无脱离受管运行时的执行合同 |
| 硬件寄存器 / MMIO | 不承诺 | 无地址与解引用语义 |
| 严格硬实时 | 不承诺 | §13：回收会合与终结无最坏耗时合同 |
| 任意自定义分配器、手动释放 | 不提供 | 内存策略由编译器与运行时管理 |
| 与任意 C 结构体共享布局 | 不默认成立 | 需逐类型验证或封送（§19） |
| 动态装载/卸载托管插件 | 首发基线不包含 | 封闭链接；动态模块列为后续方向 |
| GPU 设备内存模型 | 不覆盖（明确否决） | 需独立合同，另行立项后方可支持 |

这些边界不能仅由“有没有 GC”推断；即使代码段不分配对象，也可能遭遇 GC 会合、同步阻塞或原子操作延迟。
