本文档是"运行时"的调度与并发设计。分工边界：**语言层没有 `async` / `await`，没有任务语法**（S1 §0.6）；任务闭包的内存规则在 S3 §11；取消/超时的**错误面**在 S5 §5—6；本文档定义机制侧——执行模型、任务 API 合同、取消传播、同步原语、跨任务数据规则。

## 1. 定位与核心立场

### 1.1 规范分工

| 主题 | 归属 |
| --- | --- |
| `async` / `await`、函数着色 | 拒绝（S1 §0.6），本文档确认为永久设计 |
| 任务闭包捕获、env 跨线程根、GC 保活 | S2 §14.4、S3 §11.1—11.3 |
| 跨任务共享的内存安全（发布点、原子计数） | S3 §11.3 |
| 取消的错误面（`Cancelled` 契约） | S5 §5 |
| 超时的错误面（`Timeout` 契约） | S5 §6 |
| 任务边界的错误交付形态 | 本文档 §4.4（对齐 S5 §7.1） |
| 取消机制、任务组、上下文、同步原语、调度合同 | 本文档 |

### 1.2 核心立场

- 并发是库能力，不是语法能力。并发代码与顺序代码形态一致：函数返回 `Result`，取消与超时是 `Err`，没有第二种控制流。
- 结构化优先：任务必须归属于显式任务组；组的生命周期约束任务的生命周期（§4）。不提供自由浮动（detached）任务。
- 数据竞争是程序错误：运行时不做检测、结果不作任何保证（非承诺；原因：不做竞争检测；依赖后果：存在数据竞争的程序不受任何行为保证，S3 §11.3）；同步责任在使用点显式。
- 不承诺调度公平性与实时性（对齐 S3 §0、S5 §6.2）；承诺的是确定性行为合同：取消到达、超时生效、组关闭前任务终结。

### 1.3 与 XDK 的边界（示意绑定声明）

本文档中出现的 `xdk.*` 包名（`xdk.tasks`、`xdk.sync`、`xdk.ui`）、类型名（`Task`、`TaskGroup`、`Context`、`Mutex`、`Channel`、`Atomic*`）与函数签名（`spawn` / `join` / `close` / `checkCancel` / `withDeadline` 等，含附录 A 全表）以第 6 部分（XDK v1.0.0）为准，本部分只规定其**语义与机制**：执行模型与调度合同（第 2 节）、结构化并发约束（第 4 节）、取消/超时传播机制（第 5、6 节）、同步语义与使用规则（第 7 节）、跨任务数据规则（引用 S3 第 11 节）、运行时行为边界（第 8 节）。`@tasks` 块注解的语义（第 2.3 节）是规范性的；注解名变更走第 6 部分版本流程。

## 2. 执行模型

### 2.1 线程与任务

- 线程是运行时资源；任务是调度与取消的单元。任务到线程的映射（M:N、1:1 或混合）由实现决定，语言不承诺。
- `main` 是根作用域的持有者：入口函数体内的任务组构成任务树的根（§4.2）。
- 任务闭包进入 `xdk.tasks` 时，env 登记为 external root，任务存活期间保证可达；任务终结时移除（S2 §14.4、S3 §11.1）——本文档将其细化：**"任务存活"= 从提交到组确认终结**，见 §4.4。

### 2.2 调度合同

- 调度器保证：已提交的任务最终被调度或被取消；被取消的任务最终终结（无饥饿孤儿）。
- 任务内的阻塞分为两类：
  - **任务感知阻塞**（XDK I/O、锁、通道、join）：调度器挂起任务，不占用线程；
  - **任务无感知阻塞**（FFI 调用、未知原生代码）：占用载体线程直到返回。第 7 部分 §7.3 已为长阻塞调用规定"提交给专用执行器"的合同；本部分确立区分原则。
- 任务内代码不得假设执行线程；线程归属需求（如 UI 主线程）由 `xdk.ui` 用显式调度到指定执行器表达。

### 2.3 `@tasks` 块注解（S2 §16 推迟项的定义）

- `@tasks` 标注方法或块：声明其体内提交或等待任务。语义：
  - 提交任务的闭包环境按 S3 §11.1 作为 external root 处理（对逃逸分析是不可见边界，S3 §15）；
  - `@tasks` 块内可以使用本规范全部任务 API；块外使用任务 API 是编译错误。
- `@arena` 是实现侧调优注解，与 `@arc` / `@gc` 同类：非承诺入口，语义由实现文档定义，不进入本规范与验收矩阵。原名 `@memoryPool`，因命名冗长于设计期更名（未实现，无兼容负担）。

## 3. `xdk.tasks` API 合同

签名示意（实际以 XDK 规范的实现合同为准）：

```x
final TaskGroup group = TaskGroup.create(ctx);

final Task<Int> t = group.spawn(() -> Result<Int, TaskError> {
    return compute(ctx);          // ctx 经捕获进入任务
});

final Result<Int, TaskError> r = t.join();
```

### 3.1 `Task<T>`

- `Task<T>` 是任务句柄：值类型语义的不可复制票据；`join()` 只能成功一次，重复 `join` 是合同错误。
- `join()` 返回 `Result<T, TaskError>`；`TaskError.kind()` 为 `Cancelled`（组取消或上下文取消）或 `Timeout`（带截止时间的 join 超时）；任务自身的业务错误**原样**通过（§4.4）。
- `joinDeadline(deadline)` 在截止点返回 `Err(Timeout)`，任务继续执行至自身终结或被组取消（超时不自动取消——调用方显式决定，对齐 S5 §6.1"超时是调用方驱动的取消"）。

### 3.2 `TaskGroup`

- `TaskGroup` 是资源：必须在使用点显式关闭（S2 §16、S3 §17"任务组必须在使用点显式关闭"）。
- 关闭合同（`close()`）：
  1. 向所有未终结子任务的上下文发出取消（S5 §5.2 契约生效）；
  2. 等待全部子任务终结（含其清理路径完成，S5 §5.2"清理不跳过"）；
  3. 返回 `Result<void, TaskError>`：首个非取消类子任务错误（调用方决定观测，模式同 S5 §4.4）。
- 关闭是唯一终结路径：不存在"不关组就丢弃"的合法形态；`close` 未调用而作用域退出是使用错误（`defer group.close();` 是标准写法）。
- 组可以嵌套：子组关闭前父组关闭视为父组关闭的一部分（取消先序遍历传播）。

### 3.3 `Context`（上下文）

- `Context` 携带取消信号与截止时间，**显式传参**——不做隐式线程局部传播（无 TLS 隐式状态，符合显式气质）。
- `Context.background()`：无取消、无截止的根上下文（仅 `main` 与测试入口使用，定案；应用代码不得调用）。
- `ctx.checkCancel()`：返回 `Result<void, CancelledError>`；长任务必须周期性调用检查点，取消是协作式的（S5 §5.2）。
- `ctx.withDeadline(d)`：派生带截止时间的子上下文；截止触发等效取消（`Cancelled`），由调用方区分或统一按 `Cancelled` 处理。
- 惯例（非强制）：可取消 API 的首个参数是 `Context`。

### 3.4 错误交付（对齐 S5 §7.1 任务边界行）

- 子任务的业务错误**原样交付**：`join()` 把任务闭包的 `Err(E)` 值原样传给调用方，不包装、不降级 `kind()`。
- 只有组取消/超时产生的终止以 `TaskError`（`Cancelled` / `Timeout`）表达，与业务错误在类型上可区分。
- `try` 不能穿透任务边界：任务闭包内的 `try` 只能传播到闭包自己的返回（S1 §10.2 闭包规则）；跨边界传递只能经 `join()` 的 `Result`。

## 4. 结构化并发（决策项）

**本规范采纳作用域化任务组**：`group.spawn` 是创建任务的唯一方式；不存在游离于组之外的任务。

- 任务树与调用树同构：组在作用域内创建，任务不比组活得久；"后台任务泄漏"在语言层面不可能发生。
- 取消自动向下传播：取消组 → 全部子任务（S5 §5.2"框架级取消向上传播的保证"由此落实为向下取消 + 关闭等待）。
- 不采纳的形态（记录留痕）：全局 `spawn` / 线程池直接提交 / detached 任务。需要守护型后台工作时，用长生命周期组表达（如应用级组挂在 `main` 根作用域），生命周期依然显式。

## 5. 取消机制（机制侧，对接 S5 §5）

- 取消信号经由 `Context` 传递；`TaskGroup.cancel()` 与上下文截止是仅有的两个取消入口。
- 取消是协作式：任务在检查点响应取消；无检查点的 CPU 密集任务只能在下一个检查点前继续运行——合同是"取消最终生效"（组关闭会等待终结），不是"立即中断"。
- 取消传播链：组取消 → 子任务上下文取消 → 任务闭包内 `checkCancel()` 返回 `Err(CancelledError)`（`kind()` = `Cancelled`）→ 任务以 `Err` 终结 → 组关闭的 `join` 收敛。
- 清理路径（`defer` / `errdefer`）在取消后的执行不受取消影响（S5 §5.2"清理中的取消请求排队"）；清理期间需要 I/O 时使用不受该上下文取消的独立上下文。

## 6. 超时机制

- 定时器由调度器提供；`Context.withDeadline` 与 `joinDeadline` 是仅有的两个超时入口。
- 超时触发的语义与取消同构（S5 §6.1）：副作用停止、清理不跳过、错误分类为 `Timeout`（joinDeadline）或 `Cancelled`（上下文截止）。
- 精度边界沿 S5 §6.2：不早于到期点后尽快生效；无硬实时承诺。

## 7. 同步（`xdk.sync`）

### 7.1 最小原语集

| 原语 | 形态 | 合同 |
| --- | --- | --- |
| `Mutex<T>` | 数据携锁：`Mutex<T>` 包裹共享数据 | `withLock((T) -> Result<R,E>)` 作用域化访问；不提供裸 lock/unlock 对（防忘解锁）；锁内不得再锁同锁（死锁自负，无检测承诺） |
| `Channel<T>` | 有界通道 | `send` / `receive` 均为可取消挂起点（`Result` + `Cancelled`）；关闭后 `receive` 返回确定终态；是任务间数据流的首选形态 |
| `AtomicInt` / `AtomicBool` / `AtomicRef<T>` | 原子单元 | `load` / `store` / `compareExchange`；顺序一致性，不暴露内存序参数（可预测优先，弱序需求属实现边界） |

### 7.2 使用规则

- 跨任务共享可变状态必须经 `Mutex` / `Atomic` / `Channel` 之一（S3 §11.3"调用方负责同步"的具体化）；不可变快照（构造后不再写入的对象图）无需同步，是推荐的默认共享形态。
- 锁与任务：`withLock` 体内可以 `checkCancel`，但锁内的取消处理必须在解锁后完成重操作；不得在锁内 `join`（死锁风险自负）。
- `Mutex<T>` 的 `T` 不得是 `struct`（值复制会绕过互斥）；经 `Mutex` 共享的类对象按 S3 §11.3 原子计数管理。
- 不提供 `Condvar`（首版）：等待语义用 `Channel` 表达；确有需求时按次版本演进。

## 8. 运行时行为边界

- **任务内 panic**：终止整个进程，不做任务级隔离（S1 §10.4"不可捕获"、S4 §3.4"进程边界"）。服务型隔离按进程模型设计（每请求一进程或监督进程，属工程配置规范）。
- 任务转储（诊断所有存活任务及其等待点）是实现侧诊断能力：输出形态**非承诺**（原因：调试信息结构属实现自由；依赖后果：不得在工具或脚本中依赖其格式），不进入语言合同。
- 载体线程数、调度参数等属实现配置（工程配置规范固化）；语言程序不得假设具体线程数。

## 9. 实现边界与发布门槛

- `xdk.tasks` / `xdk.sync` 未实现前，任何声称支持并发的 XDK 包（网络、文件异步 I/O）不得发布。
- 任务感知阻塞与任务无感知阻塞的区分清单必须由第 7 部分（FFI 入口 `@blocking` 声明，§7.3）与第 6 部分（XDK 包文档）逐 API 声明（§2.2）。
- GC 安全点必须覆盖任务挂起点：任务挂起/恢复路径上的引用交换必须经过发布点（S3 §11.3），验收覆盖。
- 本规范验收通过前，S4 能力缺口表中"多线程任务"（调度、阻塞、取消、关闭、线程归属）与"异步处理"（结果交付、超时、取消、资源关闭）两行维持"未落实"状态。

## 10. 验收矩阵

| 编号 | 领域 | 验收内容 | 判定 |
| --- | --- | --- | --- |
| TASK-01 | 任务 | `spawn` 仅经组；无组任务无法创建；`join` 一次性；业务错误原样交付、kind 不降级 | 编译错误或运行时合同测试 |
| TASK-02 | 任务 | 组 `close`：取消全部子任务并等待终结（含清理路径完成）；未关组退出作用域被拒绝 | 运行时合同测试 |
| TASK-03 | 任务 | 任务闭包 env 在任务存活期间可达，终结后回收（对齐 S3 §11.1） | GC 压力测试 |
| TASK-04 | 任务 | 任务内 panic 终止进程，无任务级隔离 | 进程级测试 |
| CANCEL-01 | 取消 | 组取消向下传播；任务经 `checkCancel` 以 `Cancelled` 终结；无检查点任务在关闭时仍被等待 | 运行时合同测试 |
| CANCEL-02 | 取消 | 清理路径在取消后完整执行；清理中取消排队 | 运行时契约测试（对接 S5 CANCEL-02） |
| TIMEOUT-01 | 超时 | `joinDeadline` 返回 `Err(Timeout)` 且不自动取消；上下文截止触发 `Cancelled` | 运行时合同测试 |
| SYNC-01 | 同步 | `Mutex.withLock` 作用域化；锁内逃逸 Guard 被拒绝；`Mutex<struct>` 被拒绝 | 编译错误 |
| SYNC-02 | 同步 | `Channel` 关闭终态确定；`send` / `receive` 可取消 | 运行时合同测试 |
| SYNC-03 | 同步 | 原子操作顺序一致；跨任务共享未经同步容器被识别为逃逸（保守按 GC） | 运行时测试（对接 S3 §11.3） |
| SCHED-01 | 调度 | 阻塞分类清单覆盖全部 XDK 阻塞 API；任务感知阻塞不占载体线程 | 实现声明 + 测试 |
| BLOCK-01 | 块注解 | `@tasks` 块外使用任务 API 被拒绝；块内提交按 external root 处理 | 编译错误 |

## 附录 A. API 合同总表（`xdk.tasks` / `xdk.sync`）

| API | 所属包 | 一句话合同 |
| --- | --- | --- |
| `TaskGroup.create(ctx)` | `xdk.tasks` | 创建任务组；资源，必须 close |
| `group.spawn(closure)` | `xdk.tasks` | 提交任务；唯一创建方式 |
| `group.cancel()` | `xdk.tasks` | 取消全部子任务（不等待） |
| `group.close()` | `xdk.tasks` | 取消 + 等待全部终结；返回首个非取消错误 |
| `Task<T>.join()` | `xdk.tasks` | 等待终结并交付 `Result<T, TaskError>` |
| `Task<T>.joinDeadline(d)` | `xdk.tasks` | 带截止等待；超时返回 `Err(Timeout)`，任务继续 |
| `Context.background()` | `xdk.tasks` | 根上下文（main/测试） |
| `ctx.checkCancel()` | `xdk.tasks` | 协作式取消检查点 |
| `ctx.withDeadline(d)` | `xdk.tasks` | 派生带截止的子上下文 |
| `Mutex<T>.withLock(fn)` | `xdk.sync` | 作用域化互斥访问 |
| `Channel<T>` | `xdk.sync` | 有界通道；挂起点可取消 |
| `AtomicInt/Bool/Ref` | `xdk.sync` | 顺序一致原子单元 |

## 附录 B. 决策留痕

| 决策 | 采纳 | 未采纳（留痕） |
| --- | --- | --- |
| 结构化并发 | 任务必须归属组；组关闭是唯一终结路径 | 全局 spawn、线程池直提、detached 任务 |
| 取消传递 | `Context` 显式传参 | 隐式 TLS / 隐式传播 |
| panic 隔离 | 无（进程边界） | 任务级 panic 捕获、监督树（归工程配置） |
| 锁形态 | `Mutex<T>` 数据携锁 + `withLock` | 裸 lock/unlock、重入锁 |
| 等待协调 | `Channel` 优先 | 首版 `Condvar`（可次版本追加） |
| 内存序 | 顺序一致固定 | 暴露 acquire/release 等内存序参数 |
