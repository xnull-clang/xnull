## 3. 大文件：native xparser 段错误（阻塞，非本卡可修）

| 入口 | native xparser | 说明 |
|---|---|---|
| `impl/lib/b2/xparser.x`（自解析，2094 行） | **rc=139（SIGSEGV）**，0 字节输出 | 首个失败文件 |
| `impl/lib/b2/xlex.x`（1500 行） | **rc=139**，0 字节 | 同上 |
| `impl/xnfmt/xnfmt.x`（856 行） | **rc=139**，0 字节 | interp 路径可完整生成并与 oracle 一致 |

定位过程（全部只读诊断，未改 runtime/codegen）：

1. `backtrace` 注入：崩溃在 `xn_Cls_Parser_parsePostfix +8853`，即 `xn_concat` 调用返回后写入本地槽位；
   调用链 `parseExpr → parseTernary → parseBin ×12 → parseUnary → parsePostfix`，无死循环。
2. 输入二分（xlex.x 前缀）：≤300 行稳定通过；**320 行必崩**；600 行可通过；800/1000/1200/1500 必崩
   —— 非单调，典型的堆内存安全/回收问题，而非深度或大小阈值。
3. 关掉生成的 C 里的 GC 安全点（`XN_GC_SAFEPOINT_THRESHOLD` 调到 2^40）后：xlex.x 能跑出 239512 字节，
   但 xnfmt.x 变为 rc=142（SIGALRM/abort），320 行前缀 rc=134（abort）——**不是单一 GC 触发点**。
4. `-O0/-O1/-Os` 与 64MB 栈下均复现 → 与优化/栈无关。

结论：这是 **runtime（`rt_std_text` 的 concat / 根集合）或 native codegen 的缺陷**，属 E5/E4 域；
本卡边界（只改 xparser.x、tests/b4、handoff）内无法修复，已停止继续自解析。

## 4. 另一个真实语义缺口：`\uXXXX` 转义

xparser 的词法层只支持 `\n \t \r \\ \" \' \0`，不支持 Go 的 `\xHH / \uHHHH / \u{…}`。
`impl/lib/b2/xlex.x`、`impl/lib/b2/xparser.x` 各有一处 `"\u0000"`，导致（**即使走 interp**）：

```
oracle: (Text "\x00")
xparser: (Text "u0000")     ← 比 oracle 少 1 个字符（多 1 字节输出）
```

修 xparser 侧需要"码点 → String"的能力，而语言面当前没有：`Bytes` 只有
`fromString/get/set/push/append/slice/length`（无 `toString`），`String` 无 `fromCharCode`，
`StringBuilder.append` 只吃 String —— 构造 `\x00` 这类控制字符无路可走（`TY-105`）。
属语言面缺口（E2/前端域），本卡边界内不可修。

因此：`xparser.x` / `xlex.x` 即便解决段错误，仍会与 oracle 差这 1 字节；`xnfmt.x` 在 interp 下已一致。
