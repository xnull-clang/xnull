## 第 1 条　两项指标冲突的裁决

### 1.1 生成物首行的 Python 字符串（指标 7）

**裁决：保留，作为已冻结的 golden 头；不计为“Python 残留”，但必须登记为例外。**

| 项 | 内容 |
|---|---|
| 事实 | `impl/internal/devtool/resources.go` 生成的 C 文件首行含 `impl/tools/gen_resources.py`，该行是 Python golden 的一部分 |
| 判定 | 这是**历史生成器名注释**，不是可执行引用、不是依赖、不参与构建 |
| 指标 7 口径 | “无 Python 残留” = `impl/**` 下 `.py` 文件为 0 **且** 无 Python 执行依赖；允许生成物注释中出现 1 处历史脚本名 |
| 收口 | S0-25 完成后另发 S0-27b（可选）把该行改为 `xnull dev res` 并重取 golden；**不阻塞本次 B-full 门** |

### 1.2 mtime 依赖（指标 3、4）

**裁决：这是阻塞缺陷，新增 S0-27，必须在 S0-24 门之前修复。**

| 项 | 内容 |
|---|---|
| 事实 | `specs.go:287` 用 `cnInfo.ModTime().After(enInfo.ModTime())` 判断英译是否滞后；干净 clone 的检出顺序随机，必然出现误报 |
| 影响 | 硬指标 3/4（两种布局 `xnull dev check` 通过）在干净 clone 上不可稳定复现——这是**假红**，与假绿同样不可接受 |
| 修法 | 改为**内容或版本判定**：比较中英规范头部版本号 + 记录在案的母本内容哈希（或 git blob hash），禁止依赖 mtime |
| 验收 | ① 打乱文件 mtime 顺序 3 次，check 结果完全一致；② 内容真变更时仍能报“英译滞后”；③ 干净 clone 上两种布局均通过 |
| 依赖 | S0-21d 完成后开工；S0-24 门前必须通过 |
| 主责 | E6；必签 QA1 |

## 第 2 条　两布局验收的执行方式

worktree 不含被忽略的 `xnull/`，因此“公开布局”验收不能直接在工作树里跑。统一规定：

1. E6 在 S0-21d 产出**已构建二进制** `evidence/S0-21d/bin/xnull`（附 sha256）。
2. 工作区布局：以主树 `/Users/vjs/Desktop/XNull-Lang` 为 cwd，运行该二进制 `dev check`。
3. 公开布局：以 `/Users/vjs/Desktop/XNull-Lang/xnull` 为 cwd，运行同一二进制 `dev check`。
4. QA1 独立复跑，不引用 E6 的输出当结论；两次运行的命令、cwd、sha256 全部入证据。

## 第 3 条　测试时限

E6 自测 `go test ./...` 必须加硬界：`go test ./... -count=1 -timeout 180s`。超时如实记为 P0-2 证据，不得无限等待，不得用 `-short` 掩盖。
