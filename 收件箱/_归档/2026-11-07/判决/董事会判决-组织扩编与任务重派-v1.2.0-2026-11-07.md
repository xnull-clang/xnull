# 董事会判决：组织扩编与任务重派 v1.2.0

> **判决版本：v1.2.0**　**判决日期：2026-11-07 00:20**　**性质：董事会正式判决，具约束力**
> **替代关系：本判决替代 v1.0.0 任务执行报告的「编制」「WIP」「主责分配」；任务卡 ID 与 E1–E8 门标准继续有效。**
> **v1.0.0 / v1.1.0 文件冻结不动。本件不得修改；修订另发 v1.2.1。**
> **触发：用户裁决「这些人不够，太少了，干活的人要重新洗牌」。**

## 第 0 条　判决摘要

**批准扩编与洗牌。** 现行 2 个执行者承载 101 锚点、43 张任务卡，WIP 已饱和，且两人共用一棵脏工作树——这是结构性瓶颈，不是态度问题。

新编制：

- **2 个 CTO 保留，但退出“唯一干活的人”角色**，转为领域责任人与架构评审；
- **新增 6 个执行组（E1–E6）**，每组一个写入域，WIP=1；
- **新增 1 个独立质量组（QA-1）**，只写测试与验收，不写生产代码，向 CEO 报告；
- CEO、COO、董事会、用户不变。

一句话：**CTO 负责“对不对”，执行组负责“做出来”，QA 负责“证明做对了”。三权分立，不再一个人既写又验。**

## 第 1 条　为什么必须洗牌（证据）

| 证据 | 事实 | 后果 |
|---|---|---|
| 任务量 | 43 张任务卡，Stage 0 约 10.4 人日、Stage 1 约 27 人日 | 2 人串行，至少 5–8 周 |
| WIP | CTO-1=1、CTO-2=2 已满 | 新任务只能排队，无法并行 |
| 单点 | interp、codegen、cli、runtime、ffi、xdk 全压在 2 人 | 任一人阻塞，全线停 |
| 脏树 | 2 人共用一棵工作树，13 项未提交 | 互相覆盖，无法定位回归 |
| 验证 | 实现者自验 | 假绿无法被发现 |
| 结果 | `.xn` 穿透 7 次验收、5 道门 | 门失效的根因之一是“没人独立验” |

**结论**：不是加两个人就能解决，而是要把“写、审、验”拆开，把写入域切开，把工作树隔开。

## 第 4 条　工作树隔离与合并门

### 4.1 隔离

- 每组一个独立 worktree：`wt/e1-front`、`wt/e2-sema`、`wt/e3-interp`、`wt/e4-codegen`、`wt/e5-runtime`、`wt/e6-toolchain`、`wt/qa-1`。
- 每组一个分支：`pod/e1-front` … `pod/qa-1`。
- **禁止直接写 `main`**；`main` 只接受合并。

### 4.2 合并门（四条全过才合并）

1. 该分支 CI 九项全绿（带 sha 与 artifact）；
2. 文件所有者在场评审，确认无跨域改动；
3. QA-1 抽跑至少一条验收命令；
4. CEO 签字。

### 4.3 合并窗口

- 每日 **18:00–19:00** 统一合并；紧急合并需 CEO 单独授权。
- 合并冲突由**文件所有者**解决；跨域冲突升级 CTO/CEO。
- 合并后 `main` 必须再跑一次 CI，红则回滚该次合并。

### 4.4 启动顺序（防止“六个人一起把树弄乱”）

**11-07 上午先建 CI，下午才允许并行写代码。**

1. 09:00–12:00：E6 建 CI 骨架；其他组只做只读审计、写任务计划、完成交接，**不写生产代码**。
2. 12:00–18:00：E6 把 CI 九项跑通；S0-01 工作树盘点 + S0-02 基线 tag 完成。
3. 18:00：合并门开启，各组才可开工写代码。
4. 18:00–24:00：E3 修 break、E4 修多文件、E6 修 `main(args)`、E1/E2 做条款审计。

## 第 8 条　产能与关键路径

| 项 | 旧编制（2 执行者） | 新编制（6 执行组 + QA） |
|---|---|---|
| Stage 0 | 约 3 个日历日 | **约 2 个日历日**（CI 是关键路径） |
| Stage 1 | 7–10 个日历日 | **5–7 个日历日**（受合并门与审计依赖限制） |
| 并行度 | 2 | 6 写 + 1 验 |
| 单点风险 | 高 | 中（E6 是新的关键路径） |

**不承诺线性的 3 倍提速**。新增人手带来合并、接口、评审成本；保守估计有效提速 **1.8–2.5 倍**。真正决定速度的仍是条款 ID 与 CI，不是人数。
