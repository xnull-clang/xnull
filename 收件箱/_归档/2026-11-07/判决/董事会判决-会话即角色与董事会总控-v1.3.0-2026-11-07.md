# 董事会判决：会话即角色与董事会总控 v1.3.0

> **判决版本：v1.3.0**　**判决日期：2026-11-07 00:25**　**性质：董事会正式判决，具约束力**
> **替代关系：本判决修订 v1.2.0 第 2–4 条的「会话模型」、v1.0.0 任务执行报告的「派工载体」、`会话命名与通讯约定-v1.0.0` §1.1 的「一任务一会话」隐含前提。**
> **任务卡 ID、验收标准、E1–E8、文件所有权矩阵继续有效，不变。**
> **本件冻结，不得修改；修订另发 v1.3.1。**
> **触发：用户裁决「一个会话就是一个角色，每个会话都支持多个任务并发；资源要利用好；董事会是项目大总管，所有会话由董事会控制和管理」。**

---

## 第 0 条　判决摘要

**批准「会话即角色」模型，董事会升格为项目总控。**

三条硬规则：

1. **一个常驻会话 = 一个角色**，不是一张任务卡。任务卡是这个会话的工作队列，不是会话的身份。
2. **会话之间真并行**：每个会话是独立进程，董事会可同时向 N 个会话投递，不需要排队等一个跑完。
3. **会话的建、命名、迁移、设模型、派工、轮询、收菜、验收、重启、归档，全部由董事会执行**；执行会话不得自建会话、不得互相派工、不得绕过董事会。

一句话：**会话是岗位，任务是工单；董事会派工单，不派人。**

---

## 第 1 条　先纠正三个错误模型

| 错误模型 | 表现 | 后果 | 正确模型 |
|---|---|---|---|
| **一卡一会话** | 每张任务卡新建一个会话，43 张卡就可能 43 个会话 | 会话爆炸、上下文重复加载、资源浪费、无人对结果负责 | 一个角色一个常驻会话，任务卡进队列 |
| **会话即任务** | 会话名带任务卡 ID，任务完成会话就废 | 换卡必须新建会话，历史上下文丢失 | 会话名带角色，任务卡在台账里流转 |
| **标题即进度** | 靠会话标题判断在做什么 | 标题不改就永远“看起来在忙” | 进度只看台账 + 回执 + sha |

**v1.2.0 的真实问题不是“人少”，是“把会话当任务用”。** 6 个执行组不等于 6 个任务，而是 6 个岗位；每个岗位可以连续处理几十张卡。

## 第 3 条　命名修订（覆盖约定 v1.0.0 §1.1）

| 类型 | 格式 | 示例 |
|---|---|---|
| **常驻角色会话**（默认） | `<角色>-<角色名>` | `E3-解释器组`、`QA1-独立质量组` |
| 专项会话（仅当需要隔离上下文，如高风险实验、外包审计） | `<角色>-<任务卡ID>-<任务名>` | `E4-S1-06-多文件前向声明` |
| 重启常驻会话 | `<原名称>｜重启<N>-<本次任务>-<YYYY-MM-DD>` | `E3-解释器组｜重启1-接续break修复-2026-11-07` |

规则：

1. **默认用常驻会话**；任务切换不改名、不新建。
2. 专项会话必须有书面理由（董事会批准），完成后归档，不转正。
3. 禁止「新会话」「临时」「测试」「未命名」。
4. 会话名不含任务卡 ID，任务卡在台账里。

## 第 4 条　并发模型（为什么可以“多任务并发”）

### 4.1 三个层次的并发

| 层次 | 机制 | 上限 | 说明 |
|---|---|---|---|
| **会话间** | 每个会话独立进程，董事会用 `prompt` 异步投递 | 11 个角色会话同时跑 | 这是真正的并行，互不阻塞 |
| **会话内（写）** | 一个会话同时只推进一张写代码的卡 | WIP=1 | 防止自己踩自己，保证可定位 |
| **会话内（读）** | 同一会话可并行只读审计、查资料、跑只读命令 | 不限 | 只读不产生冲突 |

**结论**：并发的单位是「角色」，不是「任务」。11 个角色同时干活，等于 11 条流水线；每个角色内部一次只焊一个点。

### 4.2 董事会投递方式

| 场景 | 手段 | 同步性 |
|---|---|---|
| 首次派工 / 长任务 | `prompt` API 异步投递 | 立即返回，后台跑 |
| 等结果收菜 | `GET /api/session/<id>` 轮询 `outcome` + `time.idle > time.busy` | 轮询 |
| 需要立即拿答复 | `opencode run -s <id> -m <model>` | 同步阻塞 |
| 追问 / 纠偏 | 再次 `prompt`，同一会话续上下文 | 异步 |

**禁止**：董事会用同步 `run` 串行等 11 个会话——那是把并行又活成了串行。

### 4.3 会话内队列

每个会话的消息就是队列。董事会一次只投一张卡，附完整上下文；上一张卡 `idle` 且回执落了，再投下一张。**不堆消息**，堆了会乱序执行。

## 第 5 条　董事会总控六步循环

```
① 盘点  读台账 + 各会话状态（outcome / busy / idle / cost）
② 派工  写任务卡 → prompt 投递 → 台账置“进行中” → 记录投递时间
③ 轮询  每 N 分钟查一次；超时未 idle → 判卡住
④ 收菜  读回执 + 证据目录 + sha；不读聊天记录当证据
⑤ 验收  交独立验收人（QA-1/必签人）；董事会只签 L4
⑥ 改派  通过→台账置“通过”并投下一张；打回→回 ②；两次打回→换组
```

**董事会不写生产代码，不替执行组修 bug，不代替 QA 跑验收。** 董事会只做四件事：定标准、派工、收证据、换人。

### 5.1 状态判定（唯一口径）

| 状态 | 判定 |
|---|---|
| 空闲可派 | `outcome` 存在且 `time.idle > time.busy` |
| 在跑 | `time.busy > time.idle` 或无 `outcome` |
| 卡住 | 在跑但超过 ETA 2 小时无新消息 → 读 `/message` 判断是否空转 |
| 失败 | 最新 idle 的 `outcome != succeeded` |
| 锁死 | `model` 不是 `opencode/deepseek-v4.1-flash-free` → 先复位再投递 |

**注意**：`/message` 是倒序（最新在前），取 `data[0]`。

## 第 6 条　会话台账（唯一权威）

文件：`收件箱/会话台账-v1.0.0-2026-11-07.md`，由董事会维护，**每个动作后立即更新**。

必填字段：

| 字段 | 说明 |
|---|---|
| 角色 | E1–E6 / QA1 / CTO1 / CTO2 / CEO / COO |
| 会话 ID | `ses_…` |
| 标题 | 必须与命名规范一致 |
| 目录 | 当前 worktree 路径 |
| 模型 | 必须是 `opencode/deepseek-v4.1-flash-free` |
| 状态 | 待命 / 在跑 / 卡住 / 失败 / 锁死 / 归档 |
| 当前卡 | 任务卡 ID，无则 `—` |
| 下一张卡 | 队列头 |
| 最近投递 | 时间戳 |
| 最近收菜 | 时间戳 + sha |
| 成本 | `cost` + `tokens` |

**台账与看板冲突时，以台账为准；台账与回执冲突时，以证据目录为准。**

## 第 7 条　派工协议（每条消息必须包含）

```text
【任务卡】S0-18 建 7 个 worktree 与分支
【角色】E6
【写入域】ci/**、wt/**、.git（只读操作）、收件箱/E6/**
【输入】HEAD sha、7 个分支名
【要做】逐条列出，不超过 7 条
【验收】可复制命令 + 期望输出
【证据】evidence/S0-18/ 七件套
【停止条件】任一命令失败、发现跨域冲突、>2h 无进展 → 停手并回执
【禁止】改 main、改他人文件、commit/push、改测试
【回执】收件箱/E6/回执-S0-18.md，五行
```

缺任一项，执行会话应**拒收并回报**，不得自行脑补。

## 第 8 条　收菜与验收分离

| 角色 | 能做 | 不能做 |
|---|---|---|
| 执行组 | 写代码、写测试、自测、交证据 | 给自己签验收、改门标准 |
| QA-1 | 独立跑命令、抽样、判不通过 | 写生产代码、被 CTO 要求“改绿” |
| CTO | 技术评审、定架构、会签 | 替执行组写卡、替 QA 签字 |
| CEO | 派工、门禁、解阻 | 降低阈值、放行无证据交付 |
| 董事会 | 判决、换人、改标准 | 写业务代码、替 CEO 签门 |

## 第 9 条　故障处置

| 故障 | 处置 | 时限 |
|---|---|---|
| 会话锁在错误模型 | `POST /model` 复位到 `opencode/deepseek-v4.1-flash-free` | 立即 |
| 会话卡住（在跑但无进展） | 读 `/message` 判断；空转则投“停止当前动作并回执” | 30 分钟 |
| 会话失败（outcome ≠ succeeded） | 读错误，修复后重投同一张卡 | 1 小时 |
| 同一会话连续 2 次打回 | 该组解散，任务并入兄弟组，CTO 连带 | 董事会决定 |
| 会话上下文过长/失忆 | 新建 `<原名>｜重启N-…`，先投一页交接摘要 | 1 小时 |
| 会话被误删 | 重建同名会话，从台账 + 最近回执恢复 | 30 分钟 |

## 第 10 条　资源纪律（不浪费的具体定义）

1. **不重复建会话**：同一角色只允许一个常驻会话，除非董事会批准专项会话。
2. **不空转**：待命会话不投无意义消息；派工即带完整任务卡。
3. **不复用错误**：任务切换不改名、不新建，只更新台账。
4. **不串行等**：董事会用 `prompt` 并派，不用 `run` 一个个等。
5. **不浪费上下文**：长任务把细节写进文件，消息里只给路径和验收，不贴大段代码。
6. **不做无证据的活**：每张卡必须产出 `evidence/<task-id>/` 七件套，否则视为没干。
7. **成本可见**：每次收菜记录 `cost`/`tokens`；单卡成本异常（>10 倍中位数）要复盘。
8. **用完归档**：专项会话完成即归档；自检会话确认无在途后删除（删除是破坏性操作，需用户授权）。
