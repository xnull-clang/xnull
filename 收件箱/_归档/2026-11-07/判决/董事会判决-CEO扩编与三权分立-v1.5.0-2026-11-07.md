# 董事会判决：CEO 扩编与三权分立 v1.5.0

> **判决版本：v1.5.0**　**判决日期：2026-11-07 02:55**　**性质：董事会正式判决，具约束力**
> **触发：用户裁决「一个 CEO 不够，继续扩招更多的 CEO」。**
> **替代关系：本判决修订 v1.2.0 第 2.1 条「CEO 一人」与 v1.3.0 第 2 条编制表中的 CEO 行；其余条款继续有效。**
> **本件冻结，不得修改；修订另发 v1.5.1。**

---

## 第 0 条　结论

**批准扩招：CEO 从 1 人扩到 3 人。但不是三个 CEO 抢同一支笔，而是把 CEO 的三项权力拆开，一权一主。**

| 角色 | 权力 | 一句话 |
|---|---|---|
| **CEO1** | 门禁与验收 | 只判「通过 / 不通过」，不派工、不改缺陷状态 |
| **CEO2** | 派工与调度 | 只派工、管 WIP 与会话，不签门、不改验收结论 |
| **CEO3** | 整改与证据 | 只追缺陷、查证据、管整改，不派工、不签门 |

董事会仍是唯一终审与换人权。三个 CEO 之间**没有上下级**，只有分工；冲突一律升级董事会，不许互相签、不许互相推翻。

---

## 第 1 条　为什么要扩，不扩会怎样

| 现状 | 后果 |
|---|---|
| 一个 CEO 同时管派工、门禁、缺陷、证据、解阻 | 任务排队；S0-21 到 S1-22 期间门禁与整改互相等 |
| 同一人既派工又签门 | 自己派的活自己放行，独立性不足 |
| 同一人既签门又改缺陷状态 | ERR-005（CI 未入库却被当作通过）这类失效无人复核 |
| 用户要求继续扩招 | 不扩就是顶着干 |

**扩编不是加三个签字的人，是把「派、判、改」分开，让每个 CEO 只对一件事负责。**

## 第 3 条　三权边界（硬规则）

| 动作 | CEO1 | CEO2 | CEO3 | 董事会 |
|---|---|---|---|---|
| 写任务卡、投递会话 | ✗ | **✓** | ✗ | 可越过 CEO2 直接派 |
| 登记/更新任务看板 | 只读 | **✓** | 只读 | ✓ |
| 签 L1/L2 门禁 | **✓** | ✗ | ✗ | 终审 |
| 宣布「通过/不通过」 | **✓** | ✗ | ✗ | ✓ |
| 登记缺陷、改缺陷状态 | 只读 | 只读 | **✓** | ✓ |
| 关闭 ERR / P0 / P1 | ✗ | ✗ | **✓（需证据）** | 终审 |
| 证据七件套审计 | 抽检 | ✗ | **✓ 全检** | 抽检 |
| 会话模型/额度/卡死处置 | ✗ | **✓** | ✗ | ✓ |
| 公开同步授权 | ✗ | ✗ | ✗ | 用户 |
| 换人/解散组 | ✗ | ✗ | ✗ | **✓** |

**禁止**：
1. CEO2 不得在任务卡上写「验收通过」；
2. CEO1 不得为了让门通过而改缺陷状态或改测试；
3. CEO3 不得用「整改中」代替「不通过」；
4. 任何一个 CEO 不得代替另一个签字；
5. 三人意见冲突时，不得私下合并结论，必须写 `收件箱/冲突-<主题>-<日期>.md` 升级董事会。

## 第 5 条　防「三个 CEO 更乱」的五条

1. **一权一主**：同一动作只有一个 CEO 有权做，表见第 3 条。
2. **一卡一门**：一张任务卡只对应一个门禁签字人（CEO1），不得多签。
3. **看板唯一**：任务状态以 CEO2 的看板为准；门禁结论以 CEO1 的门文件为准；缺陷状态以 CEO3 的表为准。三者冲突升级董事会。
4. **每日 09:30 三句站会**：CEO1 报门、CEO2 报卡、CEO3 报缺陷；各三句，不开长会。
5. **48 小时试用**：每人至少完成 1 个本职动作（签 1 门 / 派 1 卡 / 关 1 缺陷）；连续 2 次越权或空转，降权回执行组。
