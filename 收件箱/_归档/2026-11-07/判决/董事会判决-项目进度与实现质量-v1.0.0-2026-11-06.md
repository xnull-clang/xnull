### 3.2 门失效的核心证据：`.xn` 逃逸率

**事实链**：
- 规范 S1 v3.0.0 / v3.1.0 / v3.3.0 三版一致规定扩展名 `.x`；
- 实现自 T1 起全链条使用 `.xn`，无任何偏离申报；
- `.xn` 穿透：T1、T2、T3、M1、M2、M3、M4、M4.4、M4.5、M4.6、两轮 README 评审、12 个公开 commit；
- 最终由**用户巡检**发现，非任何门禁或流程环节发现。

**判决**：`.xn` 类规范符合性缺陷的**逃逸率 = 1/1 = 100%**。这是董事会认定当前门禁体系失效的决定性证据。

**根因（采纳 CEO 复盘结论，董事会加以确认）**：
1. 门只做「执行力验证」（回执说的做了没有），不做「符合性验证」（做的符合规范吗）；
2. 以回执的诚实性替代合规性判断——**诚实 ≠ 合规**；
3. 提速激励使验收向放行倾斜；
4. 没有「规范条款 → 实现 → 测试」的机械对照工具（第六检缺位）；
5. 没有 CI，所有门都是人工时点抽样。

**董事会补充定性**：这不是 CTO-1 单点失误。T1 引入 `.xn` 是起点，但**七次以上验收、五道里程碑门、12 个公开 commit 全部放行**，说明是门设计缺陷，责任在 CEO 的门标准，不在某一个执行者。

## 第 5 条　董事会决议（具约束力）

### 决议 5.1　门禁改制（CEO 执行，即刻生效）

1. 验收结论只允许三种：**「实测通过 / 实测不通过 / 条件通过」**，必须附「实测项清单 + 未测项声明」。
2. 「质量高 / 回执质量好」等评价性用语从验收语境**停用**。
3. 每道门至少抽 3 条已审定条款做**机械对照**：源文件扩展名、入口约定、诊断码格式、关键字集合。
4. **门只认 commit sha + CI 产物**。没有 sha 的“8 包全绿”不作为验收证据。
5. 冻结 M5 / M4.5 / M4.6 新功能，直到当前树重新转绿并完成 re-gate。

### 决议 5.2　共享绿门（CTO-2 执行）

新建 CI，作为第五道门，必须一次跑完以下九项，任一红即 fail：

1. `gofmt -l` 为空
2. `go vet ./...`
3. 8 个 Go 包 `-count=1`
4. codegen 全量（含 examples 黄金对照，带硬超时）
5. C 运行时六套件（`build_rt.sh`）
6. 9 个单文件示例 + multi 工程双路径逐字节对照
7. `check_specs.py` 六检（新增第六检）
8. 台账再生成 diff 为空
9. 泄漏扫描零命中

补充要求：
- CI 必须 `-timeout 120s`，**禁止挂起**；挂起等同失败。
- CI 必须产出可下载的测试报告与二进制。
- 第六检覆盖「规范-实现条款一致性」：扩展名、CLI 入口、示例命名、诊断码前缀，任一不符 exit 非 0。

### 决议 5.3　`.x` 全量整改顺序（CTO-1 执行）

**批准的顺序，不得调换**：

1. 修 P0-1 break 传播（`loopBody` 返回信号：break/continue/normal），补四类回归：直接 break、嵌套 if break、标签 break、for-in break；补编译↔解释差分用例。

3. 跑通「8 包 + codegen + 9 示例 + runtime 六套件」，拿到绿。
4. 再做 `.xn` → `.x` 全量改名（代码、示例、自举素材、multi 子目录、import 引用、测试扫描模式）。
5. 双路径复测逐字节一致。

**理由**：603s 挂起与扩展名无关。先改名不改 break，只会把红门带进 `.x` 时代。
