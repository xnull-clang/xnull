## 3. 未达成项与原因

### 3.1 全绿未达成：`TestTupleCodegenRuns`（预存在，E4 域）

```
tuple_test.go:93: cc 失败：exit status 1
  p.c:396:57: error: unknown type name 'xn_tup_int64_t_int64_t'
```

- 在 `699c625`（无 `.a`、直编 C 源）上复现同样报错 → **不是 libxnrt 引入**，也不是 B2-04 auto 前端引入（go 前端同样失败）。
- 根因：`impl/internal/codegen/codegen.go:742` 先发容器 typedef，`codegen.go:755` 才发元组结构体定义；
  数组元素为元组时产生前向引用。
- 处置：不动生产代码（codegen 属 E4）；已出定位与修复方向，请 E4 落 patch。修好后本卡绿灯即达成。

### 3.2 609s / 686.9s / 905s 不是 `.a` 变慢

主因是 B2-04 默认 `auto` 前端：`TestXDK07SemaSurface` 在 auto 下 >301s（user 552s 忙等），`XNULL_FRONTEND=go` 下 **1.77s**；
`internal/cli` 全包 auto → 601s（10m 超时，`TestXDK07SemaSurface` 挂起 8m55s），go → **108.47s 全绿**。
建议测试环境统一 `XNULL_FRONTEND=go`，需要验证 auto 的用例显式设置。

其次是机器争用：

6 个失控 `xnull run --interp ../impl/lib/b2/xparser.x ...` 进程（B2 脚本无超时，goto/while 挂起）各占 20–210% CPU
约 2 小时，叠加其他会话并发跑全量，load average 一度 40+。已 `kill -9` 清理；清理后同一命令 134.71s。
建议：B2 的 interp 调用加超时（如 `perl -e 'alarm 60; exec @ARGV'`），防止再次拖慢全机。

## 4. 结论：保留 `.a` 链接改动（**已由 S8-21c 推翻，见 `回执-S8-21c.md`**）

依据：同一工作树、同一命令、同一前端下，源编译 286.20s → 链接静态库 134.71s，且失败集合完全一致（仅预存在 tuple）。
`.a` 不慢，单测进程还省掉 7–10s 的运行时重编。
