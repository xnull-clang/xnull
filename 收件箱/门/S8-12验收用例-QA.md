## 0. 判定口径

| 项 | 规则 |
|---|---|
| 单例判定 | 退出码 + stderr 诊断码 + 产物/`.xmeta` 断言三者同时满足才记 PASS |
| 退出码 | 0 成功；1 构建失败（validateIntegrations/编链/测试失败）；2 清单或用法错误（XPD-3xx、XPD-2xx） |
| 失败即停 | 每个负例只允许出现预期诊断码；出现其它 XPD 码即 FAIL（用例已注明允许并存的除外） |
| 工程隔离 | 每个用例独立目录，互不共享 `target/`、`xnull.lock`、`XNULL_REPO` |
| 复现性 | 同一工程连续构建两次，`.xmeta` 字节一致；`lock --update-lock` 连续两次锁字节一致 |
| 禁止项 | 不改产品代码；不改 `impl/`、`bindings/`；只写 `tests/s8/s812/` 与 `evidence/S8-12-E2E/` |

`app/xnull.project`：

```text
project {
  groupId = s812
  artifactId = app
  version = 1.0.0
  packaging = app

    dependency g:top {

`app/src/main/x/main.x`：

```

`app-managed/xnull.project`：在 `app` 基础上加（注意 management 必须嵌套 `dependencies` 段）

```text

        version = 1.0.0
      }
    }
  }
```

`app-conflict/xnull.project`：依赖 `g:a 1.0.0`、`g:b 1.0.0`，入口文件同 `app`。
`app-cycle/xnull.project`：依赖 `g:c 1.0.0`。

### 3.3 正例命令与断言

```sh
export XNULL_REPO=/Users/vjs/Desktop/XNull-Lang/tests/s8/s812/f2-dep-lock/repo
cd tests/s8/s812/f2-dep-lock/app

/tmp/xnull-s812 lock --update-lock        # 期望：已生成 xnull.lock：2 条（g:lib 2.0.0、g:top 1.0.0）
/tmp/xnull-s812 lock                      # 期望：锁有效：…（2 条）
/tmp/xnull-s812 build                     # exit 0，stdout 为产物绝对路径
/tmp/xnull-s812 run                       # F2-TEST 不存在时仅运行主程序：F2-MAIN-OK
```

| 断言 | 方法 |
|---|---|
| 传递依赖入锁 | `grep -c "coordinate" xnull.lock` ≥2；含 `g:lib`、`g:top` |
| 锁条目字段 | `kind = dependency`、`repository = central`、`sha256` 为 64 位十六进制 |
| `.xmeta.lockSha256` | 等于 `shasum -a 256 xnull.lock` 的值 |
| 锁可复现 | `cp xnull.lock /tmp/l1`；再 `--update-lock`；`cmp /tmp/l1 xnull.lock` 无差异 |
| 管理版本优先 | 在 `app-managed` 执行 `lock --update-lock` → 选中 `g:lib 1.0.0`（非 `2.0.0`） |
| 构建产物真实 | `test -x target/app-1.0.0`；`.xmeta` 中 `lockSha256` 非空 |

### 3.4 负例

| ID | 构造 | 命令 | 期望 |
|---|---|---|---|
| F2-N1 | `app-lockbad` 锁只写 `g:top`（缺传递 `g:lib`） | build | exit 1，`XPD-404`（锁缺条目） |
| F2-N2 | 锁额外加 `g:extra 1.0.0`（图内无此坐标） | build | exit 1，`XPD-405` |
| F2-N3 | 锁中 `g:lib` 的 `sha256` 改为 64 个 `0` | build | exit 1，`XPD-406`（制品摘要不符） |
| F2-N4 | 清单改依赖 `g:top 2.0.0`，锁仍为 1.0.0 | build | exit 1，`XPD-404`（版本不一致） |
| F2-N5 | `app-conflict` 执行 `lock --update-lock` | lock | exit 1，`XPD-403`，消息含 `g:a@1.0.0`、`g:b@1.0.0`、`g:x@2.0.0`、`g:x@3.0.0` |
| F2-N6 | `app-cycle` 执行 `lock --update-lock` | lock | exit 1，`XPD-409`（依赖环） |
| F2-N7 | `app-badver` 依赖 `g:lib {}`（缺版本） | lock | exit 1，`XPD-401` |
| F2-N8 | `app-badver` 依赖 `g:lib` 版本 `"[1.0,2.0)"`（必须带引号） | lock | exit 1，`XPD-402` |
| F2-N9 | `app-managed` 同时显式写 `g:lib 2.0.0` | lock | 成功并输出覆盖管理版本的警告（`res.Warnings`），锁仍 1.0.0 |

> 说明：依赖图冲突/环只在 `xnull lock` 或“存在 xnull.lock 的 build”路径校验；无锁 build 不报 XPD-403/409。用例统一用 `lock` 触发。

### 3.5 手工构造锁（N1/N2/N3）

### 4.6 不可达/不适用（记录，不签 FAIL）

| 项 | 原因 | 处理 |
|---|---|---|
| `XPD-604` 缺失必需键、`XPD-605` 类型不符 | build 集成把清单 `configuration` 全部按 `KindString`，无 Required/Int 规格 | 沿用 `internal/config` 单元证据（PROJ-08 已签）；E2E 不适用 |
| `XPD-804` pom 声明资源 | `resolveEntry` 对非 app 先报 `XPD-201`，资源校验未执行 | 待 S8-14 聚合 reactor 后补 E2E；本卡不签 |
| `XPD-608` 非 app 含配置文件 | 同上，非 app 在入口阶段即失败 | 同上 |
| 依赖资源合并 / starter 不合并 | 依赖未链接 `.xlib`（S8-13） | 待 S8-13 后补；本卡不签 |
| parent 本地仓库/远程定位 | 仅 `relativePath`（S8-13） | 本卡只验 `relativePath` |
| `xnull lock --profile` | lock 命令不接 profile | 不在本卡用例内；记录为命令面缺口 |

### 4.7 已知风险（签 PROJ-07 前需确认）

| ID | 现象（main `9c4f51e` 实测） | 影响 | 处理 |
|---|---|---|---|
| R1 | 只要资源根存在 `application-<p>.properties`，而该 profile **未被 `--profile` 激活**，build 报 `XPD-607`（build 把 `Resolved.ActiveProfiles` 传给 config 的 `Spec.Profiles`，而 `ActiveProfiles` 只含已激活项，不含“已声明未激活”项） | 声明了 dev profile、平时不加 `--profile` 的工程会被判配置错误 | 本文件按现状把 dev 文件限定在 F3-b；PROJ-07 签核时需确认 S8 §6.1 语义，若应为“声明即可”则记缺陷给 E6 |
| R2 | 键名含 `key`/`token`/`password`/`secret` 段（如 `unknown.key`）即使只是未知键，也会同时触发 `XPD-606` | 负例键名选择会影响期望诊断码 | 未知键负例统一用 `unknown.setting`；密钥负例单独用 `db.password` |
