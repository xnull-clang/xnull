## 一、诊断：董事会为什么转不动（证据）

### 1.1 文档自增殖远超工程产出

| 维度 | 实测 | 问题 |
|---|---|---|
| 收件箱体量 | 655 个文件（236 md / 178 out / 118 err） | 单一目录无层级收敛，"收件箱"名存实亡 |
| 回执箱 | 280 个文件 | 每个 2 小时任务一张回执，回执数 ≫ 有效决策数 |
| 董事会判决 | **两天内 13+ 份**（v1.0.0 → v1.9.1，含 v1.7.x 三连版、M1 快照每小时一版） | 判决生命周期以小时计，上一版未执行下一版已签发 |
| 看板数量 | M1实时看板（120s 自动刷新）、任务看板-M1 v1.0.0/v1.0.1、M6 看板、董事会快照 v1.7.x、CEO2 视图、CEO1 视图 | **同一事实至少 4 个副本**，且已经互相不同步（M1 看板 v1.0.1 说 6/14，实时看板说 7/14） |
| 组织编制 | 全员 32 岗（董事会任务列表-全员32岗） | 32 个"岗位"服务一个约万行代码的项目，管理比≈岗位数/提交数 |
| 决策积压 | 待办-04 三质询未答复、EXP-001–021 待回、GEN 回执在问"M1 与 B0 先后"、用户裁决队列（提案-001、HN 账号等） | 全部汇入单一仲裁点=董事会=用户时间 |

### 1.2 三个根因

1. **治理层自服务**：董事会/CEO2/CEO3 的产出物是"看板、快照、判决、台账"，这些产出物又需要新的看板和快照来跟踪——文档在管理文档，没人写编译器。M1 六个锚点从 03:50 到 13:23 官方计数几乎未动，而同期治理文档增加了几十份。
2. **无单一事实源（SSOT）**：状态的真实值在 git log 和测试结果里，但没有任何一个视图直接从 git/CI 生成；每个会话手工维护自己的副本，于是出现"6/14 还是 7/14"这种不该存在的争论。
3. **单点仲裁 + 批处理决策**：所有阻塞（跨域冲突、优先级、规范修订）都排队等董事会/用户。决策是批处理的（攒一批 24 小时回一次），而工程阻塞是实时发生的——Little 定律直接失效，在途事项只增不减。

## 二、业界方案对照（推荐直接采纳的部分用 ★ 标）

| 业界实践 | 来源 | 核心思想 | 对 XNull 的适用度 |
|---|---|---|---|
| ★ **WIP 限制 + 拉动系统** | 精益/看板方法（Kanban） | 在途事项上限=产能；完成一件才拉新一件 | **最高优先**。现状是"全员 32 岗、每岗都有卡"，实际并行有效工作≈4–5 人。WIP 总数应设为真实人数 +1 |
| ★ **单一看板 / 单一 backlog** | Scrum/看板共识 | 一个团队一块板，状态只有一列制事实 | 砍掉 5 套看板，只留 1 块**从 git + CI 自动生成**的板；手工看板全部废止 |
| ★ **架构决策记录（ADR）** | Rust/Microsoft/GitLab 普遍实践 | 决策=一个短文件（背景/决定/后果），不可变、只追加 | 替代"判决 v1.x 每小时一版"：判决文件写完即冻结，变更=新 ADR，禁止同文件连环升版 |
| ★ **单线程所有者（STO）** | Amazon | 每个目标一个 owner 全链路负责，不设中间管理岗 | 替代 32 岗：4–5 条**流对齐线程**（见第四节），每条一个 owner，董事会不派工只管门 |
| **错误预算 / 门禁预算** | Google SRE | 预算耗尽自动停止发布、全部转修稳定性 | 映射到门预算：EXP-016 的预算修正本质是这件事；预算超支自动降级并行度 |
| **DORA 四指标** | DORA/DevOps 研究报告 | 度量交付结果（前置时间/频率/失败率/恢复时间），不度量文档数量 | 汇报口径换成：commit 数、测试绿数、锚点翻转数；禁止以"发了 N 份文件"为产出 |
| **Conway 定律镜像** | Team Topologies（Skelton/Pais） | 组织结构应镜像目标架构：单体编译器 → 少量流对齐团队 + 1 个平台组 | 32 岗违反此律：管理层数 > 代码模块数。自举期最合理的结构见第四节 |
| ** handbook：异步默认 + 一切皆 MR** | GitLab | 决策异步化、书面化、与代码变更绑定 | 治理意见不进聊天/收件箱，直接以 MR 评论挂在对应代码/规范变更上 |
| **分级响应** | SRE 事件分级 | P0 实时响应、P1 当日、P2 周 | 解决"批处理决策"：只有 3 类事允许打断用户，其余 owner 自决 |

## 三、组织重构建议（32 岗 → 5 线）

```
用户（唯一裁决点：门禁放行 / 死命令 / 预算）
 │
 董事会（缩编为"门禁委员会"：只做三件事）
 │   ① 门判定（B0–B4、M1–M5，凭证据）
 │   ② 冲突仲裁（仅在 owner 之间无法解决时）
 │   ③ ADR 归档与发布审查
 │   —— 不派工、不看板、不写快照
 │
 ├─ 前端线（owner：现 RD 线主力）   xfront + sema：M1 收口 + 泛型（EXP-001）
 ├─ 自举线（owner：现 codegen 主力） codegen + B0–B4 准备（EXP-005/006/007）
 ├─ 运行时线（owner：现 CTO-2）     rt/gc/ABI + M3 收尾（EXP-012）
 ├─ QA 线（owner：QA1）             独立验收 + 黄金用例库（EXP-004）；QA 不得与 RD 同源
 └─ 发布线（owner：COO）            README/公开内容；不碰代码（既有边界维持）
```

- **CEO1/CEO2/CEO3 三层管理层撤销**，其职能并入董事会（门判定）与各 owner（派工）。
- 被裁撤的 32 岗中，约 20 个是"看板维护、快照同步、台账登记"岗——**全部由脚本替代**（见 4.2），不是由人替代。
- 线内 WIP=1（每 owner 同一时刻最多 2 张卡：1 开发 + 1 等验收）。

## 四、机制重建（可直接开工的四件事）

### 4.1 决策瘦身：三类令牌制

- **ADR**（原"判决"）：背景/决定/后果三段，≤40 行，签发即冻结；
- **门判定**：只发生在 M1–M5 / B0–B4 检查点，输入=证据包，输出=过/不过 + 一句话；
- **用户裁决**：仅限死命令、预算、公开发布三域；其余由 owner 在 ADR 记录后自决。
- 预期效果：董事会两天 13 份判决 → 每周 3–5 份 ADR。

### 4.2 状态单一事实源（SSOT）：脚本生成，禁止手写

用现有 `impl/tools/gen_ledger.py` 思路扩展一个 `gen_board.py`：
- 输入：git log + `go test ./...` + 台账 status.tsv + 门证据目录；
- 输出：唯一一块看板（M1 锚点表 + B0–B4 门表），每次 CI 运行自动重写；
- **手写看板、每小时快照、120s 自动刷新器全部废止**；看板不可手改——手改即作废。
- 这同时消灭"6/14 vs 7/14"类分歧：状态只有 git 与测试两个源头。

### 4.3 决策响应 SLA（替代 24 小时批处理）

| 级 | 定义 | 响应 |
|---|---|---|
| P0 | 门禁点阻塞 / 规范冲突导致停工 | ≤2h，owner 直接问用户 |
| P1 | 跨线冲突、EXP 中的 blocker | 当日 |
| P2 | 清理、文档、诊断质量 | 周批，ADR 集中处理 |

### 4.4 汇报口径换指标（DORA 化）

董事会例会（如有）只看四个数：
1. `git rev-list --count`（本周提交）
2. 锚点翻转数（PASS 增量）
3. 测试全量绿/红
4. 门进度（B0–B4 / M1–M5 各一句话）
**禁止汇报文档数量、看板更新次数、回执张数。**

## 六、一句话
