## 一、EXP-006（P-09 句柄面）

### 事实核对

- FFI 运行期层已具备句柄/Bytes/错误码编组：`impl/internal/codegen/ffi/emit.go` 的 `KindBytes`（:329，借用 + canary）、`KindHandle`（:354，借入/`.transfer`/`.reclaim`/close 幂等）、`@errorCode` 出参（:300-310）均已实现；标量映射覆盖全部整数/浮点/Bool/Char（`emit.go:60-95`）。
- 缺口只在 **codegen 的 P-09 注入层**：`impl/internal/codegen/ffi_gen.go:97-125` 的 `ffiSupported` 只放行 `void/Int/Int64/String`，句柄、Bytes、`@errorCode` 一律跳过。
- 跳过路径只打印提示，调用点最终以“未定义标识符（RES-101）”失败：`impl/internal/codegen/build.go:69-71`。
- B1 文本子集路径确实存在且闭环：`bindings/xdk/sys.xfb:70-79` 的 `readFileText`/`writeFileText`；实现 `impl/runtime/rt_std_sys.c:179,221`；P-09 对 `String→String` 与 `(String,String)→Int` 可注入。B1-02 的 XNull 实现即调用这两个 API（`git show c3d5ca6:impl/xnfmt/xnfmt.x:765-767`）。
- 当前注册表实为 **15 条**入口（新增 `readFileText`/`writeFileText`/`fileOpenWrite`），早期交接提到的 12 条已过期。

### 判定

**同意** ADR-001 的“B1 仅用文本 API 子集、句柄面列入 B2 前必清”。专家“XNull 版会被迫绕道”的推断不成立：不必用全局缓冲，文本整文件 API 已够 `xnfmt`；B1-03 的 5 处差异是格式化规则问题，与本项无关。

### 会签条件

1. B2 开工前必须完成句柄/Bytes/`@errorCode` 的 P-09 注入，验收面为：XNull 源码调用 `fileOpenRead → fileRead → fileClose`，编译路径可执行，错误码映射为 `Result` 且未知码归 `Internal`。
2. 不支持入口不得只靠 `RES-101 未定义标识符` 暴露；必须给出 FFI 专用诊断（入口名 + 原因 + 位置），否则 B2 无法区分“拼写错误”与“未实现”。
3. `readFileText` 失败返回 `null`、无错误分类（`sys.xfb:70` 注释），B1 可接受，但 `xnfmt` 必须把 `null` 当失败显式报错，禁止当空文件；B2 必须改为 `Result/ErrorKind`。
4. 句柄面转正前，`.xfb` 的 15 条入口清单要同步到 CI 与台账；入口数变化不应只体现在测试常量里。

## 二、EXP-010（协议→GC 保守判定）

### 事实核对

- 判定表行 2：`protocol` 无实例、分析按 GC（S2 §15.1，`XNull解决方案-第2部分-对象编程-v3.3.0.md:1580`）。
- 行 5：类强引用字段含协议/`Any`/`Object`/未单态化泛型/含引用元组/`Result` → GC（同上）。
- §15.1.1 现有保守性只有三条：环含 GC 节点改判 GC、不可见边界按逃逸、不可分析归 GC（:1591-1595）；**没有“判 GC 后不可逆”的表述**（全库 `grep 不可逆` 为零）。
- §15.2 明确：栈分配是优化，不改变语义；不逃逸的局部类对象可以栈分配（:1614 起）。这与专家建议的“不可再判 ARC/**栈**”字面冲突。
- 实现侧：sema 已把协议字段归 `gc`（`impl/internal/sema/policy.go:98` 附近）；codegen 对含 GC 字段的类 `scan` 尚未接入，显式报错（`impl/internal/codegen/classes.go:8-9`）。即“协议字段类”当前根本不可端到端编译。

### 判定

**条件同意**。需要“判定不可逆”来防确定性漂移，但必须限定作用域，不能把 §15.2 的合法优化一并禁掉。

### 会签条件

1. 条款措辞限定为：**策略判定不得从 GC 降级为 ARC/na-gc；不得因优化开关、调用点或分析阶段不同而重新判定**。判定输入固定为单态化后类型图 + 逃逸分类，输出 rule/policy 确定（DET-01）。
2. **不得禁止 §15.2 的栈分配优化**。若要禁止“GC 类对象栈分配”，必须另立条款并同步修订 §15.2/§14.2，否则规范自相矛盾，实现可以合法选择任一侧。
3. 协议字段的传染边界要写清可观察范围（字段→外层类、容器元素、闭包环境、任务环境），并作为公开性能边界；但“传染”不能推出“所有持有者永久 GC”以外的结论。
4. 验收行建议并入 MEM-01/MEM-02 或新增 `MEM-xx`；测试必须包含“同一输入、不同优化选项 → 相同 rule/policy”，否则不可逆条款无法机器验收。
5. 本条款落地 ≠ GC 可用：GC 类型 `scan` 未接、codegen 显式报错期间，能力表不得标“GC 已支持”，只能标“判定已定案、执行面未接”。

## 三、EXP-011（并发可见性与任务×FFI）

### 事实核对

- S5 §1.2 只有“数据竞争不作任何保证”（`第5部分:33`）；全篇无 `happens-before` / 可见性 / 顺序保证条款（grep 为零）。
- S5 §7.1 原子操作已明确“顺序一致性，不暴露内存序参数”（`:136`）。因此专家“连全序都没有”表述不准确：**原子有 seq_cst，缺的是锁/通道/任务边界的 happens-before**。
- S7 §5.2：trampoline 创建时把 env 登记为根，入口 `task_root_bind`，销毁时注销（`:152-154`）；但未规定任务内创建时绑到任务根还是全局根，也未规定取消/超时/组关闭时的注销责任。
- S3 §22 列了 `task_root_bind/unbind`（`:329`），未给任务根与全局根的关系定义；MEM-09 只验“env external root 绑定与解除正确”。
- 实现现状：`impl/runtime/xrt_abi.c:77-79` 把 `xrt_task_root_bind/unbind` 直接映射到 `rt_gc_root_add/remove`；`test_abi.c:99-106` 的注释明写“任务根（trampoline env 语义同全局根）”，只验证根计数，不验证任务生命周期。运行时尚无 per-task 根集合，`rt_gc.h` 也无对应结构。

### 判定

**条件同意**。补最小可见性条款必要；任务×FFI 的根登记必须同时定案“绑定到哪、何时解绑”，否则 M5 会把 alias 语义固化进实现。

### 会签条件

1. 最小可见性条款至少覆盖四条边：`Mutex.withLock` 解锁 → 后续加锁；`Channel.send` → 对应 `receive`；任务组 `close/join` 返回 → 其后读取可见；原子操作 seq_cst（把现有 §7.1 上升为显式可见性承诺）。`spawn` 前写入对子任务是否可见必须二选一写死（保证或明确不保证并给替代同步）。
2. 任务根规则必须写死：任务内创建的 trampoline env 绑定到**任务根**而非全局根；取消、超时、组关闭、异常/清理路径都必须解绑；注销后回调属合同违规（对齐 S7 INV-FFI-6）。
3. 若短期保留“任务根 = 全局根”的 alias，规范必须显式写明并证明“取消后不留下悬垂根”；否则 M5 必须引入 per-task 根集合。两种选择不能靠实现注释默认。
4. 验收行：新增 `SYNC-04`（可见性四边）或并入 SYNC-03；扩展 MEM-09/TASK-03 覆盖“取消路径解绑 + 压力下不泄漏根”。只测 bind/unbind 计数不算通过。
5. 调度器未落地前，S5 并发能力维持“未落实”；不得用当前 alias 测试结果声明任务根语义已验证。

## 四、EXP-012（ABI v1 冻结时点）

### 事实核对

- `impl/runtime/xrt.h:4` 仍写“符号与签名一经定稿冻结为 ABI 承诺”，无“候选冻结”标注；`impl/docs/runtime-contract.md` 的 P-08 也按已采纳表述。
- numeric 编组不经过 `xrt.h`：全部在绑定包装层完成（`emit.go:60-95` 的 `scalarC` 覆盖整数/浮点/Bool/Char；Bytes/句柄见 `emit.go:329,354`），包装层已有测试（`internal/codegen/ffi/xdk_text_test.go` 等）。因此 **numeric/handle 端到端失败不会迫使 `xrt.h` 改字段或签名**，失败点在 `ffi_gen.go` 注入层（见 EXP-006）。
- 真正的 ABI 前置缺陷是两组契约/实现不一致（详见 `收件箱/CTO2/交接-E5E6-2026-11-07.md` §三）：
  - R-01：`rt.c:57` 把完整对象指针传给 `deinit`，`xrt_abi.c:115` 的 `handle_deinit` 按载荷解析 → 已关闭句柄仍误报泄漏（已实测复现）。
  - R-06：`xrt.h:34-35` 把 `deinit/scan` 参数写成 payload，`rt.h:39-45` 与实现是完整对象指针；`rt.c:79` 的 `RT_TYPE_STRING.payload_size=0` 与实际布局不符。
- 文档覆盖声明失真：`impl/docs/ffi-contract.md:112` 称 `test_abi.c` 覆盖 `xrt_handle`，但 `test_abi.c` 零处引用 `xrt_handle`（实测 grep 为空）；`:142` 又以 `test_abi.c` 为关闭句柄规则用例，实际无此用例。
- 弱表语义也有歧义：S3 §16 要求“清除后的槽位必须可复用”，而 `xrt_weak_clear` 实际调用 `rt_weak_destroy` 释放槽位（`rt_weak.c:43-57`），clear 后不能再 read/rebind。

### 判定

**条件同意“候选冻结”**，但不同意“numeric 可能迫使 ABI 升 v2”的推断。ABI 转正判据应从“numeric 变体通过”改为“注入层端到端 + 契约/实现一致性 + 句柄真用例”。

### 会签条件

1. `xrt.h` 与 `runtime-contract.md` 标注为 **ABI v1 候选冻结**；转正判据四条同时满足：① codegen 注入层 numeric + handle + `@errorCode` 端到端；② R-01/R-06 关闭；③ `test_abi.c` 真正覆盖 `xrt_handle` 的 close 幂等、已关闭取原生指针为 NULL、泄漏诊断；④ `ffi-contract.md` 状态表与实测一致。
2. R-01 必须二选一统一：让 `deinit` 接收完整对象指针（与 `rt.h` 一致，改 `handle_deinit` 与 `xrt.h` 文本），或让终结链传 payload（改 `rt.c` 与所有 deinit 实现）。**不能只改 `handle_deinit` 一处**。从既有合同看推荐前者。
3. 字符串描述符语义写死：`RT_TYPE_STRING.payload_size=0` 只能表示“仅身份、不可用于 `xrt_alloc`”，或提供专用工厂并在 `xrt_alloc` 显式拒绝；否则生成代码按描述符分配会得到 0 载荷。
4. 弱表 `clear` 语义定案：`clear = 摘除但槽位可复用` 还是 `clear = 销毁槽位`；与 S3 §16 对齐并补用例（clear 后 read 必须安全、复用路径必须可测）。
5. 候选期内只做文本/实现对齐，不新增 ABI 符号；任何字段/签名变更一律升 v2，不借“候选”名义静默改。
