## 第 0 条　定位

专家评审是**输入**，不是判决，也不是门禁。董事会负责：

1. 把材料备齐、版本钉死；

3. 该改的改，该驳的驳，该问的问；
4. 最终由用户保留裁决权。

**不接受两种态度**：专家说啥都照办；专家说啥都辩护。

## 第 2 条　请专家重点回答的 12 个问题

1. **类型系统**：可空/可选提升、元组、泛型、协议，是否有不可判定的交互？复杂度是否可控？
2. **内存模型**：ARC + GC 混合、弱引用/环、FFI 句柄所有权，是否可实现且确定？
3. **错误模型**：`Result` + `@mustUse` + `try` + defer/errdefer，无异常，是否自洽？闭包内 `try` 的语义是否清楚？
4. **并发**：任务/取消/顺序/内存模型，是否足以支撑 XDK 与运行时，而不引入数据竞争？
5. **FFI/ABI**：句柄、lease、错误映射、布局、跨平台，是否有长期稳定性风险？
6. **自举**：当前语言子集是否足以写 lexer/parser/codegen？B0–B4 的门槛是否现实？删除 Go 的最大风险是什么？
7. **规范结构**：9 部分 + 10 模块 + 101 锚点，是否有重复、冲突、缺口？条款 ID 化是否可行？
8. **双路径**：解释器与编译器并存的验收方式，是否会掩盖语义分歧？
9. **工程配置**：XPD、锁、资源、插件，是否过度设计或不足？
10. **最大失败风险 Top 5**，以及建议砍掉/延后的范围。
11. **与 Go/Rust/C++/Swift/Kotlin 对比**：哪些设计是真正的新意，哪些是已知陷阱？
12. **里程碑顺序**：M1（S1 14/14）与 B0–B4 自举的先后是否合理？是否需要调整？

## 第 3 条　意见接收与处置流程

### 3.1 编号

每条意见一个 ID：`EXP-001`、`EXP-002`……

### 3.2 分类

| 类别 | 含义 |
|---|---|
| **S** 规范缺陷 | 条款矛盾、缺口、不可实现 |
| **I** 实现缺陷 | 实现偏离规范 |
| **P** 计划风险 | 里程碑、自举、资源、顺序 |
| **Q** 问题/待澄清 | 需要数据或补充说明 |
| **N** 非问题 | 已覆盖或不适用 |

### 3.3 处置表（每条必填）

```
EXP-ID：
原文摘要：
类别：S/I/P/Q/N
严重级：blocker / high / medium / low
证据：条款号 / 文件:行 / 实测
董事会判定：接受 / 部分接受 / 驳回 / 需补数据
动作：改规范 / 改实现 / 改计划 / 加测试 / 不改
主责：
时限：
用户是否需裁决：是/否
```

### 3.4 时限

- 收到意见后 **4 小时内**：登记完毕、分类；
- **24 小时内**：逐条给出判定与动作；
- 涉及规范的修改：先发新版本规范，不直接改母本；
- 涉及里程碑的修改：董事会发新判决，用户批准后执行。

## 第 4 条　纪律

1. 评审期间**冻结语义与路线**，只收意见，不边审边改。
2. 不用“专家不懂我们的场景”当反驳；也不用“专家说了”当证据。
3. 每条意见必须有证据与处置，不允许“已读”。
4. 评审结论不替代 QA 与门禁；该跑的测试照跑。
5. 用户保留最终否决权。
