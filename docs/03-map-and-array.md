# XNull Map / Array High-Performance Detailed Design

> Status: design draft v1 · 2026-11-15
> Scope: containers generated by `src/runtime/`, `src/compiler/codegen/`, the internal containers of `src/compiler/`, and `src/mini/main.x`
> Related: Design 02 (AST/Token), Design 05 (GC/ARC), Design 06 (parallel compilation)
> Algorithm selection: every implementation node lists candidate algorithms, complexity, pros and cons, and the rationale for the choice; see the "Algorithm Selection and Comparison" section.

## 1. Conclusion

The containers currently generated are "the crudest implementation that works":

- `List<T>`: object header + `len/cap` + a separately `malloc`'d `data`; initial capacity 4, `cap *= 2`; no `reserve`; `remove/insert` move elements one by one; `join` repeatedly calls `xn_concat`, O(n²).
- `Map<K,V>`: two parallel arrays `keys[]` and `vals[]`; `find` does a linear `memcmp` from 0 to len; `put` is O(n); `remove` is memmove; `keys()/values()` use insertion sort, O(n²).
- `Set<T>`: internally just a `List<T>`; `add/has/remove` are all linear scans.
- Each `K/V` combination generates a separate struct and set of functions, causing code bloat.
- The compiler's internal symbol table also makes heavy use of `List<String>` / linear search.

Goals:

- `List` push amortized O(1), random access O(1), contiguous memory;
- `Map` get/put/remove average O(1), usable with 1M entries;
- `keys()/values()` keep the current observable semantics of "ascending by key", but sort in O(n log n);
- container code converges from "one copy per type" to "generic core + type-specialized wrapper";
- compiler-internal hot paths no longer use string keys.

## 2. Current-State Evidence

### 2.1 Arrays

A typical structure generated by `Codegen.x`:

```c
typedef struct { rt_header hdr; size_t len; size_t cap; int64_t *data; } xn_arr_i;

static xn_arr_i *xn_arr_i_new(size_t cap) {
    xn_arr_i *a = (xn_arr_i *)xn_gc_new(&RT_TYPE_xn_arr_i);
    a->cap = cap ? cap : 4;
    a->data = malloc(sizeof(int64_t) * a->cap);
    return a;
}

static void xn_arr_i_push(xn_arr_i *a, int64_t v) {
    if (a->len == a->cap) {
        a->cap *= 2;
        a->data = realloc(a->data, sizeof(int64_t) * a->cap);
    }
    a->data[a->len++] = v;
}
```

Problems:

- two allocations: object and data;
- initial capacity fixed at 4, so small lists grow repeatedly;
- no `reserve`, so users cannot pre-allocate;
- `remove/insert` are hand-written loops and do not use `memmove`;
- `join` allocates a new string on every concatenation;
- `List<String>`'s `scan` visits element by element, making GC marking expensive;
- `List<T>` is a GC object, but `data` is a raw `malloc`; the GC only scans the elements and does not manage the lifetime of data (it relies on deinit).

### 2.2 Map

```c
typedef struct {
    rt_header hdr;
    size_t len, cap;
    rt_string **keys;
    int64_t *vals;
} xn_map_s_i;

static long xn_map_s_i_find(const xn_map_s_i *m, rt_string *key) {
    for (size_t i = 0; i < m->len; i++) {
        if (m->keys[i]->len == key->len &&
            memcmp(m->keys[i]->bytes, key->bytes, key->len) == 0) return (long)i;
    }
    return -1;
}
```

Problems:

- lookup is O(n), and insertion also requires an O(n) duplicate check first;
- deletion is memmove, O(n);
- `keys()` uses insertion sort, O(n²);
- string keys `memcmp` on every comparison, with no cached hash;
- `Map<String,String>`'s scan scans keys and vals together: correct, but with a large constant factor;
- `Map`'s iteration order is currently "ascending by key" (`keys()` sorting); this must be preserved unless the spec is revised.

### 2.3 Set

```c
typedef struct { rt_header hdr; xn_arr_i *a; } xn_set_i;

static int xn_set_i_add(xn_set_i *s, int64_t v) {
    for (size_t i = 0; i < s->a->len; i++) if (s->a->data[i] == v) return 0;
    xn_arr_i_push(s->a, v);
    return 1;
}
```

`Set<Int>` is O(n); `Set<String>` likewise.

### 2.4 Compiler Internals

The semantic analyzer in `src/mini/main.x`:

```x
final List<String> fnNames
final List<String> fnRets
final List<String> fnParams
final List<String> vars
final List<String> varTypes
```

Parallel arrays plus linear search. `Codegen.x`'s `fld(N, String)` also linearly scans field names.

## 3. Design Goals and Non-Goals

### 3.1 Goals

| Container | Target complexity | Target memory |
|---|---|---|
| `List<T>` push/pop | Amortized O(1) | Contiguous, no per-element nodes |
| `List<T>` get/set | O(1) | No extra allocation |
| `Map<K,V>` get/put/remove | Average O(1) | Int→Int ≤ 32 B/entry |
| `Map<K,V>` keys/values | O(n log n) | O(n) temporary |
| `Set<T>` add/has/remove | Average O(1) | Same as Map |
| Compiler symbol table | O(1) average | ID keys, no strings |

### 3.2 Non-Goals

- Do not change the language-level API (`List`/`Map`/`Set` method names and semantics remain unchanged);
- Do not introduce a user-visible hash order (`keys()` still sorts by key ascending);
- Do not build concurrent containers in the first phase (the parallel compiler uses thread-local containers, see Design 06);
- Do not require every container to support O(1) worst case (average O(1) for hash tables is enough).

## 4. Array / Vector Design

### 4.1 Layout

Two layouts are recommended, selected by element type:

**A. External data (default, compatible with a moving GC)**

```c
typedef struct {
    rt_header hdr;
    uint32_t  len;
    uint32_t  cap;
    uint32_t  elem_size;
    uint32_t  flags;        /* SBO / GC_ELEMS / ARC_ELEMS */
    void     *data;         /* points to cap * elem_size bytes */
} XnVec;
```

**B. Small buffer inline (SBO, at most 4 elements)**

```c
typedef struct {
    rt_header hdr;
    uint32_t  len;
    uint32_t  cap;
    uint32_t  flags;
    union {
        void *heap;
        uint64_t inline_[4];
    } u;
} XnSmallVec;
```

Recommendations:

- small elements such as `List<Int>`, `List<UInt16>`, `List<Char>` use SBO to avoid one malloc;
- `List<String>`, `List<Class>` use external data, where the elements are pointers;
- more than 4 elements spill to the heap automatically;
- `data` is allocated through the runtime's size-class allocator (see Design 05), not raw `malloc`.

### 4.2 Growth Strategy

```c
static uint32_t grow_cap(uint32_t cap, uint32_t need) {
    uint32_t n = cap ? cap : 8;
    while (n < need) {
        uint32_t next = n < 1024 ? n * 2 : n + n / 2;  /* 2x when small, 1.5x when large */
        if (next < n) return UINT32_MAX;              /* overflow */
        n = next;
    }
    return n;
}
```

- initial 8 (4 first when SBO);
- below 1K use 2x, reducing the number of growths;
- above 1K use 1.5x, reducing wasted memory;
- `reserve(n)` grows exactly to `n`;
- `shrink_to_fit()` is optional;
- on growth use `realloc` or the size-class `xrt_realloc`;
- overflow check: `need > UINT32_MAX / elem_size` is fatal immediately (OOM).

### 4.3 Operations

| Operation | Implementation | Complexity |
|---|---|---|
| `push` | check cap, grow if necessary; write `data[len++]` | Amortized O(1) |
| `pop` | `len--`, release ARC elements | O(1) |
| `get/set` | bounds check + index | O(1) |
| `insert(i)` | grow + `memmove(data+i+1, data+i, ...)` | O(n) |
| `remove(i)` | `memmove` + `len--` | O(n) |
| `clear` | release ARC elements one by one; `len=0` | O(n) |
| `truncate(n)` | release the tail; `len=n` | O(n) |
| `reserve(n)` | grow to n | O(n) |
| `join(sep)` | two passes: compute the total length, one allocation, `memcpy` | O(total) |
| `for-in` | cache `len/data`, index loop | O(n) |

The key point of `join`:

```c
size_t total = 0;
for (i) total += elem_str_len(a->data[i]) + sep_len;
rt_string *out = rt_string_alloc(total);
char *p = out->bytes;
for (i) { memcpy(p, ...); p += n; if (i+1<n) memcpy(p, sep, sep_len); }
```

Do not use `res = res + x`.

### 4.4 Bounds Checking

Language semantics require out-of-bounds access to be fatal (currently `xn_fatal_oob`), so it cannot simply be removed. Optimization techniques:

1. **Loop versioning**: when the compiler proves `0 <= i < len`, emit a check-free loop;
2. **Range analysis**: `for i in 0..len` eliminates the check outright;
3. **`unlikely` hint**: `if (__builtin_expect((size_t)i >= a->len, 0)) fatal`;
4. **PGO**: checks in hot loops are predicted not-taken, with branch layout optimization (Design 07);
5. **Do not ship a default `--no-bounds-check`**; if one is provided, it must be an explicit unsafe switch and must be documented.

### 4.5 Element Ownership

- `List<Int>`: value copy, no retain/release;
- `List<String>`: String is a GC object; push does not retain (the GC manages it), but `data` must be scanned;
- `List<Class>`: ARC elements; push does `retain`, pop/remove/clear do `release`;
- generic `List<T>` is described by `ElemOps`:

```c
typedef struct {
    uint32_t size;
    uint8_t  kind;              /* VALUE / ARC / GC */
    void   (*retain)(void *);
    void   (*release)(void *);
    void   (*scan)(void *, void (*visit)(void *));
} XnElemOps;
```

- codegen generates/selects the `ElemOps` for each concrete `T`;
- `List<String>`'s scan walks `data` directly;
- `List<Int>`'s scan is NULL, and the GC does not scan it.

### 4.6 Code Generation

Do not generate a complete function body for each `List<T>`. Use generic macros/inline functions in a C header:

```c
#define XN_VEC_DEF(T, Name) \
    typedef struct { rt_header hdr; uint32_t len, cap; T *data; } Name; \
    static inline void Name##_push(Name *a, T v) { ... } \
    static inline T Name##_get(const Name *a, int64_t i) { ... }
```

- the generated C expands only the specializations actually used;
- the common logic lives in `xn_containers.h`, and `static inline` lets cc inline it;
- avoid thousands of duplicated lines in the prelude;
- for `String`/pointer types, the macros expand scan/release hooks.

## 5. Map Design

### 5.1 Semantic Constraints

Currently observable behavior:

- `Map<K,V>`'s `keys()` returns keys sorted in ascending key order;
- `values()` returns values in the same order as `keys()`;
- `getOr(key, default)` returns default when the key is absent;
- `put` overwrites the old value;
- `remove` returns whether the entry existed;
- `length`, `has`, `clear`.

The new implementation must preserve these semantics. If the spec actually specifies "insertion order", the spec must be changed first, and then the implementation; this must not be changed silently.

### 5.2 Layout

A SwissTable-style open-addressing layout is recommended:

```c
typedef struct {
    rt_header hdr;
    uint8_t  *ctrl;        /* 1 B/slot: 0x80 full, 0xFE empty, 0x80|h2 */
    uint32_t  cap;         /* power of 2 */
    uint32_t  len;
    uint32_t  tombstones;
    uint32_t  key_size;
    uint32_t  val_size;
    uint32_t  entry_size;
    uint8_t  *entries;     /* AoS: [hash][key][val] */
    const XnKeyOps *ops;
} XnMap;
```

Each entry:

```c
typedef struct {
    uint64_t hash;         /* cached hash, avoids recomputation */
    /* K key; V val; follow immediately, offset by key_size/val_size */
} XnMapEntry;

#define XN_ENTRY_KEY(m, e)  ((void *)((char *)(e) + sizeof(uint64_t)))
#define XN_ENTRY_VAL(m, e)  ((void *)((char *)(e) + sizeof(uint64_t) + (m)->key_size))
```

Benefit of AoS: hash + key + value are hit in a single cache line, and string keys compare the hash before comparing the key.

### 5.3 Hashing

```c
uint64_t xn_hash_bytes(const void *p, size_t n, uint64_t seed);
uint64_t xn_hash_i64(int64_t v, uint64_t seed);
uint64_t xn_hash_u64(uint64_t v, uint64_t seed);
```

- algorithm: Wyhash or xxHash64 (short implementation, fast, good quality);
- each Map uses a random seed at creation (prevents hash DoS);
- `rt_string` gains a `uint32_t hash` cache field (see Design 05), reused after the first computation;
- `Int` keys use `splitmix64`;
- `Bool/Char` convert directly to integers;
- pointer keys mix the address, with no dereference;
- struct keys generate a hash field by field (sema generates the `hash` function).

### 5.4 Probing

- the capacity `cap` is a power of 2;
- the control byte is 1 B per slot: `0x80` means full, `0xFE` means empty, and `0x80 | h2` means full and carrying a 7-bit hash fragment;
- each probe examines a group of 16 slots (`uint64_t` bitmask or SSE2 `_mm_movemask_epi8`);
- compare the h2 in ctrl first, then the full hash, and finally the key;
- load factor 7/8 (the SwissTable default); rehash to 2x when exceeded;
- deletion uses tombstones; rehash to clean up when tombstones exceed 1/4;
- linear probing, 16 slots per group, continuing across groups.

Simplified version (no SIMD at first):

```c
static inline uint32_t map_find(const XnMap *m, const void *key, uint64_t h) {
    uint32_t mask = m->cap - 1;
    uint32_t i = (uint32_t)h & mask;
    uint8_t h2 = (uint8_t)(h >> 57) | 0x80;
    for (;;) {
        for (uint32_t j = 0; j < 16; j++) {
            uint8_t c = m->ctrl[(i + j) & mask];
            if (c == h2) {
                entry = entry_at(m, (i + j) & mask);
                if (entry->hash == h && m->ops->eq(key, entry_key(m, entry))) return ...;
            } else if (c == EMPTY) {
                return NOT_FOUND;
            }
        }
        i = (i + 16) & mask;
    }
}
```

### 5.5 Small Map Optimization

Many Maps in the compiler have only 1–8 entries (field tables, annotations, local symbols). A two-level structure:

```c
typedef struct {
    rt_header hdr;
    uint32_t len;
    uint32_t flags;       /* SMALL / HASH */
    union {
        struct { uint8_t key[8][MAX_KEY]; uint8_t val[8][MAX_VAL]; } small;
        XnMap map;
    } u;
} XnMap;
```

- linear scan while `len <= 8` (within 8 entries it is cache-friendly and faster than hashing);
- promote to SwissTable automatically beyond 8;
- `MAX_KEY/MAX_VAL` are enabled only for fixed small types; variable-length types go straight to hashing;
- for `Map<String,Int>` the key is a pointer, so `small.key[8]` just stores 8 pointers.

### 5.6 Deletion

Two schemes:

| Scheme | Pros | Cons |
|---|---|---|
| Tombstone + periodic rehash | Simple implementation, stable lookups | Tombstones consume space, degrades on long runs |
| Backward-shift deletion | No tombstones, compact memory | Complex deletion implementation, must handle probe chains |

Recommendation: tombstones in the first phase; in the second phase, if profiling shows deletion-heavy workloads, switch to backward-shift.

### 5.7 keys()/values() Sorting

Currently insertion sort, O(n²). Change to:

1. collect all entry pointers into a temporary array;
2. `qsort` / pdqsort, comparing keys (strings by byte order, Int by numeric value);
3. fill `List<K>` / `List<V>`;
4. the temporary array uses a small stack buffer (<=64) or an arena.

Complexity O(n log n). If a `Map` calls `keys()` frequently, a lazily sorted index can be maintained, but not in the first version.

### 5.8 Set

- `Set<T>` is implemented with `XnMap<T, Empty>`;
- `Set<Int>` can be specialized as a bitset (small value domain) or as Robin Hood hashing;
- `Set<String>` is the same as Map, with value_size = 0;
- `add` = `put` returning whether the entry was newly added; `has` = `find`; `remove` is the same as Map.

### 5.9 Iteration

- `for k in map.keys()` returns a sorted `List`, consistent with the current semantics;
- do not expose hash order;
- if `entries()` is added in the future, the documentation must explicitly state "order undefined";
- `keys()`/`values()` do not modify the Map.

## 6. Compiler-Internal Containers

The compiler itself also needs high-performance containers, and it should not depend on the runtime GC:

### 6.1 `Vec<T>`

```c
typedef struct {
    T       *data;
    uint32_t len;
    uint32_t cap;
} Vec;
```

- arena allocation, no per-item free;
- `vec_push` grows by 1.5x/2x;
- `vec_reserve`;
- `vec_sort` uses pdqsort;
- `Vec<NodeId>`, `Vec<SymbolId>`, and `Vec<u32>` are the workhorses.

### 6.2 `HashMap<K,V>`

- keys are `u32`/`u64`/`NameId`/`SymbolId`, not strings;
- open addressing, linear probing;
- no deletion, or tombstone only;
- iteration order is not promised, but sort before output;
- under parallelism, each thread has a local Map, merged at the end (Design 06).

### 6.3 `Interner`

See Design 02: sharding + `NameId`. The symbol table uses `HashMap<NameId, SymbolId>` and stores no strings.

### 6.4 `BitSet`

- data-flow analysis, liveness, dominator trees;
- `uint64_t words[]`;
- `bitset_and/or/andnot/count`;
- small sets use `SmallBitSet<4>` (4 words inline).

### 6.5 `WorkQueue`

- task queue for parallel compilation;
- ring buffer + atomic head/tail;
- supports work stealing (Design 06).

## 7. Interaction with the GC

- `List`/`Map` are GC objects; `data/entries/ctrl` are native memory;
- GC scan only visits elements and does not scan ctrl/hash;
- `deinit` frees the native buffer;
- if `data` is moved to a new address, the GC does not need to update element pointers (the elements are inside data);
- if a `Map`'s keys/vals are GC/ARC references, scan must visit each one;
- when a `Map`'s value is Int, scan only scans the keys;
- `List<Int>`'s scan is NULL;
- the container itself does not participate in ARC counting (it is a GC object), avoiding the complexity of mixed graphs.

## 8. Code Generation Strategy

### 8.1 Specialization vs. Generics

| Approach | Code size | Performance | Recommendation |
|---|---|---|---|
| Full generation per type | Large | Best | Hot containers only |
| Generic core + function pointers | Small | Indirect calls | Cold containers / complex types |
| Generic macros + `static inline` | Medium | Good | Default |

Recommendation: generate specializations with C macros/`static inline` by default; for complex types (struct keys) use a generic core + `KeyOps`.

### 8.2 Emit Only the Containers Used

- collect the `List<T>`/`Map<K,V>`/`Set<T>` that actually appear in the MIR;
- deduplicate by `(kind, key, value)`;
- generate in lexicographic order of type names to guarantee determinism;
- unused containers do not enter the prelude.

### 8.3 Avoiding Template Explosion

- `List<Int>`, `List<String>`, and `List<Class*>` are three specializations;
- `Map<String,Int>`, `Map<String,String>`, and `Map<Int,Int>` are three;
- do not generate `List<Class>` for every class; uniformly use `List<void*>` + a runtime type id (if the language allows it);
- fall back to the generic core above a threshold (e.g. 64 specializations).

## Algorithm Selection and Comparison (by Container Node)

> Notation: N = number of elements, C = capacity, K = key byte length, α = load factor.
> Containers are "the kingdom of constants": an O(1) linked list can lose to an O(log N) B-tree, because a cache miss costs more than an instruction.

### A1. Dynamic Array Growth

| Strategy | Amortized complexity | Memory waste | Number of growths | Pros | Cons | Conclusion |
|---|---|---|---|---|---|---|
| Fixed +1 | O(N²) | 0 | N | Saves memory | Unusable | Not adopted |
| 2x | O(1) amortized | 50% worst case | log N | Fewer growths, simple implementation | Wasteful for large arrays | Adopted for small arrays |
| 1.5x | O(1) amortized | 33% worst case | log₁.₅ N | Memory-friendly, can reuse old blocks | Slightly more growths | Adopted for large arrays |
| Golden ratio 1.618x | O(1) amortized | ~38% | log N | Fibonacci reuse possible | No clear advantage | Not adopted |
| Exact `reserve` | O(1) | 0 | 0 | Optimal | Requires knowing the size | **API provided** |

Choice: use 2x while `cap < 1024`, then 1.5x; also provide `reserve(n)`. Prefer `realloc` for growth; on failure or when a move is needed, use `malloc + memcpy + free`.

### A2. Small Containers

| Strategy | Allocations | Memory | Pros | Cons | Conclusion |
|---|---|---|---|---|---|
| Always heap-allocate (current) | 1/container | 24+ B | Simple | Even small lists malloc | Retired |
| SBO 4 elements | 0 (≤4) | 32 B inline | Zero allocation for small lists | Object gets larger | **Adopted** |
| Always inline | 0 | Fixed large | No pointer | Wasteful for large lists | Not adopted |
| Separate data + lazy allocation | 0 (empty) | Minimal | Saves on empty containers | Allocation on first push | Alternative |

Choice: small elements such as `List<Int>`/`List<UInt16>` use SBO 4; `List<String>` uses external data, because 4 pointers are still 32 B and the benefit is limited.

### A3. Hash Table Collision Resolution

| Algorithm | Average lookup | Worst case | cache | Deletion | Load factor | Implementation | Conclusion |
|---|---|---|---|---|---|---|---|
| Separate chaining | O(1+α) | O(N) | Poor (pointer chasing) | Easy | 1.0+ | Low | Not adopted |
| Linear probing | O(1/(1-α)) | O(N) | Good | tombstone | 0.7 | Low | Alternative |
| Quadratic probing | O(1/(1-α)) | O(N) | Medium | tombstone | 0.5 | Low | Not adopted |
| Double hashing | O(1/(1-α)) | O(N) | Poor | tombstone | 0.7 | Medium | Not adopted |
| Robin Hood | O(1+α) | O(N) | Good | backward-shift deletion | 0.9 | Medium | Alternative |
| SwissTable | O(1) | O(N) | Very good (16-slot groups) | tombstone | 0.875 | Medium-high | **Adopted** |
| Cuckoo | O(1) worst case | O(N) rehash | Medium | Easy | 0.5 | High | Not adopted |
| Hopscotch | O(1) | O(N) | Good | Complex | 0.9 | High | Not adopted |
| B-tree Map | O(log N) | O(log N) | Very good | Easy | - | High | Alternative for large/ordered scenarios |

Choice: SwissTable — contiguous ctrl bytes + 16-slot groups, 16 candidates compared at once, good cache locality; deletion uses tombstones, with a rehash at 7/8 load. B-trees suit Maps that need ordered iteration/range queries, and can later serve as the basis for `BTreeMap`.

### A4. Hash Functions

| Function | Throughput | Quality | DoS | Applicable | Conclusion |
|---|---|---|---|---|---|
| FNV-1a | Medium | Medium | Weak | Short keys | Not adopted |
| MurmurHash3 | High | Good | Medium | General | Alternative |
| xxHash64 | Very high | Good | Medium | General | **Adopted** |
| Wyhash | Highest | Good | Medium | General | **Adopted** |
| SipHash-2-4 | Low | Very good | Strong | Untrusted keys | Network/FFI alternative |
| CRC32 hardware | Highest | Medium | Weak | Checksums, not hashing | Not adopted |

Choice: Wyhash/xxHash64 + a random seed per Map; string keys cache their hash (`rt_string.hash`). Untrusted input (network keys) can switch to SipHash.

### A5. String Key Comparison

| Strategy | Cost per lookup | Pros | Cons | Conclusion |
|---|---|---|---|---|
| Length + memcmp | O(K) | Simple, correct | Full comparison every time | Alternative |
| Compare hash first + memcmp | O(1)+O(K), only on collision | Fast | Must store the hash | **Adopted** |
| Force intern, then pointer compare | O(1) | Fastest | Global intern cost/lifetime | Adopted by the compiler |
| Trie | O(K) | Prefix sharing | Memory/pointers | Not adopted |

The language-level `Map<String,V>` uses a hash cache + memcmp; the compiler symbol table uses `NameId` integer keys and does not compare strings.

### A6. Deletion Strategy

| Strategy | Deletion cost | Lookup impact | Memory | Conclusion |
|---|---|---|---|---|
| Tombstone | O(1) | Probe chains get longer | Needs periodic rehash | **Adopted in the first version** |
| Backward-shift | O(cluster length) | No tombstones | Compact | Second-phase alternative |
| Immediate rehash | O(N) | Best | Temporary doubling | Not adopted |
| Logical deletion + compaction | O(1) amortized | Medium | Medium | Alternative |

Choice: tombstones + rehash when the tombstone ratio > 1/4; if profiling shows deletion is frequent, switch to backward-shift.

### A7. `keys()` Sorting

| Algorithm | Complexity | Stability | Pros | Cons | Conclusion |
|---|---|---|---|---|---|
| Insertion sort (current) | O(N²) | Stable | Simple | Unusable at 100k keys | Retired |
| `qsort` | O(N log N) | Unstable | Standard library | Comparator overhead | Alternative |
| pdqsort | O(N log N) | Unstable | Fast, worst-case resistant | Needs implementation | **Adopted** |
| Radix sort (Int) | O(N·k) | Stable | Extremely fast for integers | Only suits fixed-length keys | Adopted for Int with large N |
| B-tree/ordered index | O(N) traversal | Stable | Naturally ordered | Slow insertion | Alternative for frequent `keys()` |

Choice: pdqsort in general; radix sort for `Map<Int,V>` when N > 4096. The sorted result is written into a `List<K>`, and the temporary index uses the stack/SBO.

### A8. Set Implementation

| Algorithm | add/has | Memory | Ordered | Pros | Cons | Conclusion |
|---|---|---|---|---|---|---|
| List linear (current) | O(N) | Compact | Insertion order | Simple | Slow | Retired |
| Hash Set | O(1) | Medium | No | General | None | **Adopted** |
| Bitset | O(1) | N/8 | Yes | Extremely fast | Only suits dense integers | `Set<Int>` specialization |
| Sorted array | O(log N) lookup / O(N) insert | Compact | Yes | Range queries | Slow insertion | Small/static sets |
| Bloom Filter | O(k) | Small | No | Saves memory | Has false positives, cannot be exact | Not adopted |

Choice: `Set<T>` is based on `Map<T, Empty>`; `Set<Int>` uses a bitset when the value domain is < 2^20 and dense, otherwise hashing.

### A9. Small Map

| Strategy | Lookup | Insertion | Memory | Pros | Cons | Conclusion |
|---|---|---|---|---|---|---|
| Pure hash | O(1) | O(1) | Table overhead | General | Wasteful for small tables | Large tables |
| Linear small table | O(N) | O(1) | Compact | Very fast for N≤8 | Degrades as N grows | **Adopted for N≤8** |
| Sorted small array | O(log N) | O(N) | Compact | Binary search possible | Slow insertion | Static tables |
| Hybrid (small table→hash) | O(1) | O(1) | Adaptive | Best of both | Complex implementation | **Adopted** |

Choice: linear scan while `len <= 8`; the 9th element promotes to SwissTable.

### A10. Compiler Symbol Table

| Algorithm | Lookup | Memory | Pros | Cons | Conclusion |
|---|---|---|---|---|---|
| `List<String>` parallel arrays (current) | O(N) | Large | No dependencies | Slow | Retired |
| `HashMap<NameId, SymbolId>` | O(1) | Medium | Fast, simple | Hashing overhead | **Adopted** |

| Perfect hashing (keywords) | O(L) | Small | No collisions | Only suits static sets | Adopted for keywords |

### A11. Work Queue

| Algorithm | push/pop | Memory | Parallel | Pros | Cons | Conclusion |
|---|---|---|---|---|---|---|
| Dynamic array | O(1) | Contiguous | No | Simple, cache-friendly | O(N) removal at the head | Single-threaded queue |
| Ring buffer | O(1) | Fixed | No | No allocation | Needs growth | **Adopted for single-threaded** |
| Linked-list queue | O(1) | Pointers | Yes | Lock-free friendly | Poor cache | Parallel alternative |

### A12. Sorting/Deduplication

| Algorithm | Complexity | Pros | Cons | Applicable | Conclusion |
|---|---|---|---|---|---|
| Sort + adjacent dedup | O(N log N) | Ordered results, general | Slower than hashing | General | **Default** |
| Hash Set dedup | O(N) average | Fast, no sorting needed | Unordered results, extra memory | Uniqueness only | Adopted for large N |
| Bitmap dedup | O(N) | Extremely fast, memory-efficient | Only suits small integer domains | Dense Int | `Set<Int>` specialization |
| Merge dedup | O(N log N) | Streaming, stable | Requires sorted input | Already sorted | Streaming merges |

### A13. Algorithm Selection Summary

| Node | Candidates | Choice | Main rationale |
|---|---|---|---|
| Array growth | 2x / 1.5x / golden ratio | 2x small, 1.5x large | Growth/memory balance |
| Small containers | heap / SBO / fully inline | SBO 4 | Zero allocation for small lists |
| Hash table | chaining / linear / Robin Hood / SwissTable | SwissTable | cache + load |
| Hash | FNV / Murmur / xxHash / Wyhash / SipHash | Wyhash/xxHash | speed/quality |
| String keys | memcmp / hash-first / intern | hash-first | memcmp only on collision |
| Deletion | tombstone / backward-shift / rehash | tombstone + periodic rehash | simple, controllable |
| keys sorting | insertion / qsort / pdqsort / radix | pdqsort + radix | O(N log N) |
| Set | linear / hash / bitset | hash + bitset specialization | general/dense |
| Small Map | pure hash / linear / hybrid | hybrid | fast small tables, stable large tables |
| Symbol table | List / HashMap / Trie | HashMap<NameId> | O(1) |
| Queue | array / ring / linked / deque | ring + Chase-Lev | single/parallel |
| Deduplication | sort-dedup / hash | sort-dedup default | ordered results |

## 11. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Changing Map iteration order | Keep `keys()` sorting; add semantic tests |
| Hash DoS | random seed per Map; Wyhash |
| GC scan missing values | `ElemOps` specifies the scan scope explicitly; GC stress |
| Memory bloat | 1.5x growth; `shrink_to_fit`; benchmarks |
| Code bloat | on-demand specialization + generic core + threshold |
| Parallel races | thread-local containers; merge at the end (Design 06) |
| 32-bit length overflow | `uint32_t` + overflow checks; a 64-bit variant for very large containers |

## 12. Open Questions

1. Does the language-level `Map` iteration-order spec explicitly state "ascending by key"?
2. Is `entries()` / an insertion-order view needed for `Map`?
3. Should `List<T>` allow users to `reserve`/`capacity`?
4. Should string keys be forcibly interned (can greatly speed things up, but changes memory semantics)?
5. Are concurrent Maps needed (shared across tasks)? The first version recommends not doing it; use message passing.
