## EN — "Design decision: why XNull rejects method overriding"

```
Design decision: why XNull rejects method overriding
```

In most OO languages, "which method actually ran?" is a question you answer with a debugger. You trace through three layers of a class hierarchy, half of it in a library you don't control, to find out why `widget.refresh()` didn't do what you thought.

We're designing a language — XNull — where that question is always answerable by looking at the source. This post is about the decision that buys that, what it costs, and why we published the whole reasoning.

**The decision.** Classes support inheritance as *static reuse only*. A subclass cannot redeclare a same-signature ancestor method — the compiler rejects it outright. Dynamic dispatch exists exactly once in the language: a receiver whose static type is a protocol dispatches through a vtable. Everywhere else, the method that runs is the one written in the code you're reading.

So "which method actually ran?" decomposes:

- receiver is a class type → the method defined on that class (or, if absent, the ancestor it inherited — statically visible)
- receiver is a protocol type → the single vtable slot for that protocol method

No "someone subclassed my class and changed the behavior" — because nobody can, at that call site.

**What it costs.** Being honest, this forfeits real patterns:

- **Template Method** — a base class can't let subclasses hook into its algorithm by overriding steps. In XNull you express this with composition: the base takes a protocol (the "step" interface) and delegates to it. The hooks become explicit constructor parameters — visible in the type, not buried in an override somewhere.
- **Framework "magic hooks"** — `onCreate`/`onDetach` style override-me methods. Same answer: register an explicit handler object that satisfies a protocol. More ceremony, zero surprise.
- **Patch-a-library-by-subclassing** — you can't silently fix a broken method in a dependency by overriding it. You file an issue or wrap it.

We think the trade is worth it: those patterns are exactly where "which method actually ran?" bugs come from, and the protocol/composition replacements make the seams visible. But this is the part where we most expect to be wrong.

**Where it's written down.** The full "explicitly unsupported" table with rationale is S1 §0.6 (we consider it the most important section of the spec). Class dispatch semantics and the protocol/vtable model — including the same example dispatched both statically and through a protocol — are in S2 (§5.6). Every rejection in the spec carries its rationale.

**What we're not claiming.** We're not claiming protocols make overriding unnecessary in every domain. That's an empirical bet, and it's testable: if you have a pattern that *genuinely* requires overriding — not just prefers it — bring it. A good counterargument becomes a spec revision; that's the process working, not failing.

Specs and implementation (bilingual, with a runnable interpreter): https://github.com/xnull-clang/xnull

Attack away — "here's a pattern you just made impossible and shouldn't have" is exactly the comment we want.

## 中文版（知乎）

**标题**：设计决策：我们为什么在语言层面禁止方法覆写

在大多数面向对象语言里，「这个方法到底执行的是谁」要靠调试器回答：你沿着类继承链追三层，其中一半在你控制不了的库里，才能搞清楚 `widget.refresh()` 为什么没干你以为的事。

我在设计一门语言——XNull——让这个问题永远能靠看代码回答。这篇讲清楚这个决策换来了什么、付出了什么、以及为什么把全部理由公开。

**决策本身**：类继承只做**静态复用**。子类重声明与父类同签名的方法，编译器直接报错。动态分派在整个语言里只存在一种：接收者的静态类型是协议（protocol）时，走 vtable。其余所有地方，执行的方法就是你现在读到的代码里那个方法。

于是「到底执行的是谁」可以分解为：

- 接收者是类类型 → 该类上定义的方法（没有就往上找继承来的——静态可见）
- 接收者是协议类型 → 该协议方法的唯一 vtable 槽位

不存在「有人继承了我的类、悄悄改了行为」——因为在这个调用点上，谁都改不了。

**代价（诚实列出）**：

- **模板方法模式**——基类没法让子类通过覆写某个步骤来挂钩算法。XNull 的替代写法是组合：基类持有协议（「步骤」接口），委托给它。挂钩变成显式的构造参数——写在类型上，而不是埋在某个覆写里。
- **框架式「魔法钩子」**——onCreate/onDetach 这类「请覆写我」。同样的答案：显式注册一个满足协议的处理器对象。仪式感多一点，意外少一点。
- **靠继承修补依赖库**——不能通过覆写悄悄修掉依赖里的坏方法。提 Issue，或者包一层。

我们认为这笔交易划算：上面这些模式恰恰是「到底执行的是谁」这类 bug 的产地，而协议/组合的替代写法把接缝摆到了明面上。但这正是我们最可能出错的地方。

**写在规范哪里**：完整的「明确不支持」表及理由在 S1 §0.6（我们认为这是整份规范最重要的章节）；类分派语义与协议/vtable 模型——包括同一个例子分别走静态分派和协议分派——在 S2（§5.6）。规范里每一条拒绝都附带理由。

**我们不说的话**：我们不说协议在一切领域都能替代覆写。这是个经验性赌注，而且可检验：如果你手里有一个**真的离不开覆写**的模式——不是「更喜欢」而是「离不开」——拿出来。好的反驳会变成一次规范修订，这是流程在起作用，不是失败。

规范与实现（中英双语，自带可运行解释器）：https://github.com/xnull-clang/xnull

欢迎开火——「你让某个模式变得不可能了，而它不该被牺牲」正是我们最想看到的评论。
