# ADR-010 合并冲突与重复修改的根因与修复

> 日期：2026-11-08 15:10
> 状态：生效
> 触发：用户质询「为什么有那么多冲突、经常重复修改」

## 一、根因（按事故证据）

| # | 根因 | 证据 |
|---|---|---|
| R1 | **多个会话同时写 main**：E4/E5 会自行 `merge pod → main`，与 INTEG 一次性会话并行 | 02:20 INTEG 回滚把 `35fe43b`/`019a05b` 一起 reset；19:12 main 从 `a5a635f` 被回退到 `cf3e084`，INT-01 合并被摘除 |
| R2 | **同一文件多 owner 并行**：S8-01/S8-03/S8-04 同时改 `internal/cli`，各自新增 `findManifestRoot` | 07:58 `manifest.go:47` 与 `lock.go:100` 重复定义，cli 包不可编译 |
| R3 | **派卡按功能、不按文件边界**：卡与卡之间没有先冻结接口 | S8 的 manifest/lock/lifecycle 三卡同日并行，接口靠猜 |
| R4 | **回滚策略错误**：合并测试红时 reset 到合并前，连带回滚他人已合的提交 | 02:20 P1-10 误伤；真实失败是 main 原有 `TestBND10GCMixedARCFieldValid` |
| R5 | **全局台账多写者**：status.tsv / golden 被多条线各自改 | 多次 `golden PASS 74 vs 75`、`index.lock` 争用 |
| R6 | **长卡静默 + 大批量提交**：30–60 分钟不提交，一次合入面很大 | E4 S8-04、E5 S8-07、E1 net 均出现 |

结论：**不是人员重复劳动，是合并协议与派工边界设计错误**。同一功能被多线各写一遍，是因为没有「文件所有权 + 接口先行 + 单写者」约束。

## 二、修复规则（立即生效）

1. **main 单写者**：只有 INTEG 会话可以写 main；所有生产线只允许提交到自己的 `pod/*` 分支。发现自行 merge main 的，董事会回退该合并并记 P1。
2. **合并互斥锁**：INTEG 合并前必须创建 `handoff/merge.lock`（含会话 ID + 时间），完成后删除；其他会话看到锁存在即等待。
3. **文件所有权矩阵**：每波开工前先列「卡 → 文件/包」矩阵；同一文件同一时间只允许一个 owner。跨 owner 的共享文件（如 `internal/cli`）先由一人冻结接口，另一人只调用。
4. **接口先行**：跨线卡必须先出接口文档（如 S5-00），再并行实现；没有接口文档不得并行。
5. **小卡快提**：单卡实现超过 30 分钟必须提交中间可用版本；禁止 60 分钟以上静默。
6. **红只报告不回滚**：合并测试红时保留合并结果、报告失败包/测试，由 owner 修；禁止 reset 掩盖。
7. **SSOT 单点更新**：`status.tsv`、`golden`、`BOARD.md` 只由 SSOT owner（E6）或董事会更新；其他线只提交验收文件。

## 三、当前 net 卡的文件边界（已按新规核对）

| 线 | 文件边界 | 冲突风险 |
|---|---|---|
| E1 | `impl/lib/xdk/net.x` | 无 |
| E2 | `internal/sema` net 签名 | 无 |
| E4 | `internal/codegen` net 绑定/发射、`bindings/*.xfb` | 无 |
| E5 | `impl/runtime/rt_net*` | 无 |

net 四线文件不相交，可并行；但 main 合并仍必须走 INTEG 单写者。

## 四、后果

- 合并冲突应显著下降；剩余冲突只可能来自未登记的文件边界，按 P1 处理；
- 生产线自行 merge main 视为违规；
- 本 ADR 不改变门禁口径，只改合并与派工流程。
